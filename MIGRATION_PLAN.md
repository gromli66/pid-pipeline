# План миграции P&ID Pipeline — пошагово с чекпоинтами

**Статус:** рабочий план. Текущая папка — **бэкап, код в ней не меняем**. Все правки применяются на отдельной (рабочей) копии при реальной миграции.
**Цель:** развернуть систему с локального ПК на сервер, к которому подключаются десктоп-клиенты на **Astra Linux**.
**Дата:** 2026-06-18

> Как пользоваться документом: идём по фазам сверху вниз. Каждая фаза заканчивается **Чекпоинтом** — пока он не «зелёный», на следующую (и тем более на платный сервер) не переходим. Бесплатные фазы (0–2) — до оплаты сервера.

---

## Краткая суть (TL;DR)

- Система = **сервер** (Docker-стек: postgres, redis, api, CVAT, воркеры) + **клиенты** (десктоп-UI на Astra, подключается по сети).
- Для миграции реально нужна **одна правка кода** (адрес сервера в UI) + несколько **переменных окружения** на сервере. Логика приложения не меняется.
- Сервер **CPU-only — рабочий вариант** (в коде есть `PID_DEVICE=cpu`); GPU нужен только для скорости.
- UI берёт все данные **по HTTP** (проверено) — общая файловая система не нужна, удалённый клиент корректен.
- Закрытый контур **не требует менять код** — только упаковать образы/колёса/модели заранее (Фаза 5).
- Тестируем по нарастающей: локально (бесплатно) → Astra-VM (бесплатно) → облачный Astra почасово (платно, недолго) → опционально воркеры на CPU → боевой сервер.

## Карта системы

```
        СЕРВЕР (Linux + Docker)                         КЛИЕНТЫ (Astra Linux)
 ┌──────────────────────────────────────┐
 │ postgres :5433   redis :6380          │        ┌──────────────────────────┐
 │ api      :8000  ◄──────────────────── │ HTTP   │ Десктоп-UI (PySide6)     │
 │ CVAT (traefik) :8080 ◄─────────────── │ ◄──────┤ python -m ui.main        │
 │ worker / worker_ocr (CPU)             │        │ встроенный браузер CVAT  │
 └──────────────────────────────────────┘        └──────────────────────────┘
```

Наружу клиентам нужны только порты **8000** (API) и **8080** (CVAT). Порты БД (5433) и Redis (6380) — закрыть фаерволом.

## Что именно меняется при миграции (полный перечень дельт)

Это всё, что отличает «работает локально» от «работает на сервере». Применяется на рабочей копии, не в бэкапе.

### Д1. Правка кода (одна)
`ui/windows/main_window.py:37` — адрес API зашит как `http://localhost:8000`. Сделать настраиваемым через переменную окружения (в стиле уже существующего `PID_GL_BACKEND`):
```python
import os
api_url = os.environ.get("PID_API_URL", "http://localhost:8000")
self.api_client = APIClient(api_url)
```

### Д2. Переменные окружения на сервере (`.env`)
Все три указывают на **один и тот же адрес сервера**:
- `SERVER_HOST=<IP-или-домен сервера>`
- `CVAT_HOST=<тот же адрес>` — иначе traefik (правило `Host(${CVAT_HOST:-localhost})`) не пустит запросы, пришедшие по IP, и CVAT у клиента не откроется.
- `CVAT_BROWSER_URL=http://<тот же адрес>:8080` — иначе ссылка на CVAT будет `localhost`, и встроенный браузер постучится сам в себя.
Плюс сменить пароли: `DB_PASSWORD`, `CVAT_SUPERUSER_PASSWORD`.

> **Проверено на локальном тесте (важно!):** `CVAT_BROWSER_URL` должна попасть И в `api`, И в `worker`. В базовом `docker-compose.yml` её нет ни у одного — оба используют дефолт `localhost`. Воркер строит ссылку на CVAT-задачу, и без этой переменной она уходит как `http://localhost:8080/...`, что ломается на удалённом клиенте (на одной машине незаметно). Оба получают её через `docker-compose.override.yml`.

### Д3. Токен CVAT
Токен доступа к CVAT задаётся в `.env` (`CVAT_TOKEN=...`) и читается сервисами `api` и `worker` через `${CVAT_TOKEN}`.

> **Исправлено по итогам теста на сервере:** раньше токен был ЗАХАРДКОЖЕН в `docker-compose.yml` (у `worker` — напрямую, у `api` — как дефолт `:-52db...`). Правка `.env` его НЕ меняла → воркер ходил в CVAT со старым токеном и получал `401`. Теперь оба сервиса берут `${CVAT_TOKEN}` из `.env`, и секрет не попадает в репозиторий.

На свежем CVAT старый токен недействителен. Порядок: создать суперпользователя → сгенерировать токен `docker exec cvat_server python3 /home/django/manage.py drf_create_token admin` → вписать в `.env` → `docker compose up -d api worker`.


### Д4. CSRF при сохранении разметки
Открытие CVAT (GET) заработает от `CVAT_HOST`, но **сохранение** (POST) Django может заблокировать. Решение: убедиться, что `CVAT_HOST` = тот же origin, что грузит клиент; при необходимости добавить `CSRF_TRUSTED_ORIGINS=http://<IP-сервера>:8080`; надёжнее всего — HTTPS. Точные имена переменных сверить с докой **CVAT v2.25.0**.

### Д5. Воркеры на CPU (если сервер без GPU)
- В `docker-compose.yml` закомментировать блоки `deploy.resources.reservations.devices` у `worker` (~стр. 139–145) и `worker_ocr` (~180–186) — иначе на хосте без GPU `docker compose up` для них упадёт.
- В `.env`: `PID_DEVICE=cpu`, `YOLO_DEVICE=cpu`.

### Д6. Конфиги на клиенте
Редакторы UI читают проектные YAML локально (`configs/projects/*.yaml`). Значит на каждый клиент нужно положить папку `configs/` (или раздавать через API).

> Удобный приём для Д2/Д3/Д4: вместо правки `docker-compose.yml` (он в git) использовать **`docker-compose.override.yml`** (в `.gitignore`) — добавить туда `CVAT_BROWSER_URL`, `CSRF_TRUSTED_ORIGINS` в сервис `api`. Бэкап и репозиторий остаются нетронутыми.

## Приложение A. Переменные окружения (`.env` сервера)

```
# --- адрес сервера (один и тот же во всех трёх) ---
SERVER_HOST=<IP-или-домен>
CVAT_HOST=<IP-или-домен>
CVAT_BROWSER_URL=http://<IP-или-домен>:8080

# --- БД / пароли ---
DB_USER=pid_user
DB_PASSWORD=<сильный пароль>
DB_NAME=pid_pipeline

# --- CVAT ---
CVAT_SUPERUSER=admin
CVAT_SUPERUSER_PASSWORD=<сильный пароль>
CVAT_TOKEN=<новый токен после создания суперпользователя>   # Д3

# --- устройство (CPU-сервер) ---
PID_DEVICE=cpu        # Д5
YOLO_DEVICE=cpu       # Д5

# --- прочее ---
API_PORT=8000
LOG_LEVEL=INFO
```
Клиент (Astra): запускать с `PID_API_URL=http://<IP-сервера>:8000` (+ при необходимости `PID_GL_BACKEND=software`).

## Приложение B. Риски и как их ловим

| Риск | Где всплывёт | Митигировано |
|------|--------------|--------------|
| CVAT не открывается по IP | Фаза 1/3 | `CVAT_HOST` (Д2) |
| Ссылка CVAT = localhost у клиента | Фаза 1/3 | `CVAT_BROWSER_URL` (Д2) |
| Разметка не сохраняется (CSRF) | Чекпоинт 1/3 | `CSRF_TRUSTED_ORIGINS` / HTTPS (Д4) |
| Старый токен CVAT недействителен | Фаза 3 шаг 8 | перегенерация токена (Д3) |
| Воркеры падают без GPU | Фаза 4 | `PID_DEVICE=cpu` + убрать GPU-блок (Д5) |
| Публичный IP без auth — взлом | Фаза 3 шаг 2 | фаервол только на свой IP / VPN, удалить ВМ |
| 40 ГБ диска / 16 ГБ RAM впритык | Фаза 3/4 | диск 80+ ГБ, `concurrency=1`, по одной схеме |
| Большие схемы по сети — таймауты | Фаза 3 | боевая локалка быстрее; учитывать при оценке |
| Python 3.11 / WebEngine нет на Astra | Фаза 2 | проверка заранее на Astra-VM |
| Закрытый контур без интернета | Фаза 6 | офлайн-комплект (Фаза 5) |
| Воркеры нельзя просто вынести на GPU-хост | при желании ускорить | они монтируют том `cvat_data`; нужен общий storage (NFS) |
