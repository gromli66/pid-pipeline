## 1. Обзор

P&ID Pipeline UI — десктопное PySide6 приложение для оператора pipeline. Точка входа: `python -m ui.main`.

Приложение работает как клиент к FastAPI backend (`http://localhost:8000`). Все данные (изображения, маски, графы, OCR) скачиваются через API, редактируются локально и сохраняются обратно.

**Архитектура UI:**

```
MainWindow (QMainWindow)
├─ Page 0: DiagramListWidget — список диаграмм
└─ Page 1: DiagramWorkspace — рабочее пространство
              ├─ Header: ProgressBeads + кнопки действий
              └─ Tab area: вкладка валидации/редактирования
                    └─ Editor (QGraphicsView / custom)
```

**Ключевые принципы:**

- **Навигация через QStackedWidget:** Page 0 = список, Page 1 = workspace. Внутри workspace — header (бусины + кнопки) и tab area (вкладка валидации).
- **Вкладка занимает 100% пространства:** при открытии вкладки header прячется. Кнопка «← Назад» закрывает вкладку и возвращает header.
- **Артефакты скачиваются в фоне:** каждая вкладка использует `QThread` + downloader для загрузки данных из API.
- **Autosave по таймеру:** единый `AutoSaveService` вызывает метод сохранения активной вкладки.

Настройки: `QImageReader.setAllocationLimit(1024)` — лимит 1 ГБ для P&ID изображений (до 15000×7000), стиль Fusion, высокое DPI.

## 2. Main Window

Файл: `ui/windows/main_window.py`.

`MainWindow` — корневой `QMainWindow`. Содержит:

- **Toolbar:** кнопки «📁 Загрузить» и «🔄 Обновить».
- **Progress bar:** индикатор фоновых операций (скрыт по умолчанию).
- **QStackedWidget:** переключение между списком диаграмм и workspace.
- **StatusBar:** сообщения + индикатор соединения (🟢 API / 🔴 API недоступен).

**Shared services** создаются в MainWindow и передаются в дочерние виджеты:
- `APIClient` — HTTP клиент к backend.
- `StatusProvider` — polling статусов диаграмм.

**Навигация:**
- Двойной клик по диаграмме в списке → `stack.setCurrentIndex(1)`, workspace загружает диаграмму.
- Кнопка «← Назад» в workspace → `stack.setCurrentIndex(0)`, возврат к списку.

**Загрузка диаграммы:** кнопка «📁 Загрузить» → `UploadDialog` (выбор файла + проекта) → `api_client.upload_diagram()`.

**Закрытие клиента** — `MainWindow.closeEvent` (пункт 1.18 дороги):

1. Открыта вкладка с несохранёнными изменениями (`has_unsaved_changes()`) → вопрос «Сохранить перед выходом?» с тремя ответами. «Отмена» и неудавшееся сохранение оставляют клиент открытым (`event.ignore()`), вкладка и правки на месте. **Вопрос задаёт не окно, а воркспейс** — `DiagramWorkspace.confirm_discard_active_tab()` (§3.4): вкладка его, контракт и метод сохранения — его же. Окно передаёт туда единственное, что своё у этого пути, — слово о действии («перед **выходом**» против «перед **закрытием**» у «← Назад»).
2. `DiagramWorkspace.cleanup()` — гасит опрос статуса, таймер OCR и автосохранение.
3. Строка `Клиент закрывается` в лог (§11.5); отменённое закрытие пишет свою строку.

До этого обработчика не было вовсе: крестик окна убивал процесс мимо всего — вопрос о несохранённом задавал только путь «← Назад» (`_close_active_tab`), `cleanup()` не звался, а о конце сеанса в логе не оставалось ни строки. Это же единственная точка, где накопленное клиентом успевает уйти: отсюда шлёт последний батч слой активного времени оператора (пункт 10.15).

## 3. Diagram Workspace

Файл: `ui/widgets/diagram_workspace.py`.

`DiagramWorkspace` — центральный виджет для работы с одной диаграммой. Состоит из трёх визуальных строк в header:

1. **Title bar:** название диаграммы + кнопка «← Назад» + статус + кнопка rollback.
2. **Progress beads:** цепочка бусин (см. §4).
3. **Action buttons:** 12 кнопок, по одной на каждую бусину.

### 3.1 Бусины и кнопки

12 бусин (1:1 с кнопками):

| # | Key | Кнопка | Назначение |
|---|-----|--------|------------|
| 0 | `detect` | Детекция | Запуск YOLOv8 detection |
| 1 | `cvat` | CVAT | Валидация bbox в CVAT |
| 2 | `segment` | Сегментация | Запуск UNet++ + skeleton |
| 3 | `pipe` | Вал. pipe | Валидация маски труб |
| 4 | `junction` | Вал. j/b | Валидация junction/bridge |
| 5 | `graph` | Граф | Запуск graph builder |
| 6 | `val_graph` | Вал. графа | Двухфазная валидация графа |
| 7 | `contours` | Контуры | SAM2 contour selection |
| 8 | `ocr` | OCR | Запуск OCR pipeline |
| 9 | `ocr_binding` | Привязка | Привязка OCR к графу |
| 10 | `edit_graph` | Редактор | Финальный редактор графа |
| 11 | `fxml` | FXML | Генерация FXML выхода |

### 3.2 Состояния кнопок

Каждая кнопка может быть в одном из 4 состояний (по цвету):

| Цвет | Состояние | Действие по клику |
|------|-----------|-------------------|
| Серый | Недоступна | Заблокирована |
| Жёлтый | Доступна | Запуск этапа / открытие вкладки |
| Зелёный | Завершена | Повторное открытие вкладки |
| Оранжевый | В процессе | Ожидание worker |

Состояние вычисляется функцией `_buttons_for_status(status)` на основе `_BEAD_DEFS` — маппинга бусин к статусам (completed_when, in_progress_statuses, available_when).

**Бегущая стадия глушит кнопку — кроме ручного этапа.** В «в процессе» кнопку переводит не только статус: цикл в `_update_buttons` глушит кнопку любой стадии, у которой в `/stages` есть строка `running` моложе `WAIT_LIMIT_S` (600 с). Цикл написан ради раскладки — своего статуса у неё нет, и без него её кнопка оставалась доступной во время счёта. **Из цикла исключён ручной этап текущего статуса** (`_MANUAL_INPROGRESS`): строку стадии `frame_removal` открывает сам сервер при входе во вкладку (`app/api/frame.py`, канон §8.5 RUNBOOK), а закрыть её при выходе некому — «← Назад» на сервер не ходит. Без исключения после «открыл „Очистку рамки“ → 💾 → ← Назад» кнопка гасла на 600 с, и оператор не мог вернуться к своей же сохранённой очистке (пункт 1.17 дороги). Ручной этап показывает «в процессе» по статусу — строка стадии ему для этого не нужна.

**`ERROR`: красная кнопка упавшего этапа, а при неизвестном этапе — страховка.** Основной путь (`_apply_error_status`) реконструирует прогресс по `/stages` и красит бусину и кнопку упавшей стадии. Когда `/stages` недоступен, работает фолбэк по одному значению `error_stage` через карту `_STAGE_TO_KEY`. Карта обязана покрывать ВСЕХ писателей `error_stage`, а их два вида: воркерные (`set_diagram_error`, 10 значений) и **серверные** — `app/api/cvat.py:374` пишет `fetching_annotations`. Значение вне карты давало ноль доступных кнопок из 13 (`ERROR` не входит в `_STATUS_ORDER`, поэтому в нём ни одна кнопка не «доступна» сама по себе) — оператор оставался в тупике. Теперь такое значение включает **страховочную кнопку «🔄 Повторить» в шапке** (`_offer_error_retry`): она появляется ровно тогда, когда ни одна из 13 кнопок не доступна, показывает этап и текст ошибки, а по клику зовёт `POST /api/diagrams/{uid}/retry` — карту «этап → предыдущий статус» держит сервер (`app/api/diagrams.py:448`), клиент не гадает. Порог с другой стороны: пока красная кнопка этапа есть, страховка не показывается (пункт 1.x11 дороги).

**Работа, ошибка и бусина одной задачи указывают на ОДИН этап** (блок болей 2026-08-25, боль 1/Б16). У финальной скелетизации они расходились на три: проценты и глушение кнопки шли в «Выделение труб» (`_STAGE_TYPE_TO_KEY`), бусина стояла на «Проверке узлов» (её статусы `SKELETONIZING_FINAL`/`SKELETONIZED_FINAL` лежат в наборе бусины `junction`), а ошибка красила «Проверку труб» (`_STAGE_TO_KEY`) — оператор смотрел на крутящуюся бусину одного этапа и заполняющуюся кнопку другого. Работа сведена на `junction`; перебор ВСЕХ `StageType` против трёх карт держит `tests/ui/test_stage_maps_invariant.py` — новый этап попадает в решётку сам, а связка «задача → её `error_stage`» снимается разбором `worker/tasks/` при каждом прогоне. Клетка `skeletonizing_simple` → `pipe` оставлена сознательно: так помечены строки `error_stage` у диаграмм, сломавшихся ДО переезда писателя на `skeletonizing_final` (`worker/tasks/skeleton.py`, `WORKER_TASKS §4.4`). Поэтому воркерных значений по-прежнему десять, а «понимает, но никто не пишет» стало два: `validating_graph` (значение статуса, в `error_stage` его не кладёт никто) и легаси-`skeletonizing_simple`.

### 3.3 Status polling

`StatusProvider` опрашивает backend каждые 2 секунды. При изменении статуса → `_apply_status()` → обновление бусин и кнопок. Polling останавливается на «финальных» статусах (требующих действия оператора или завершающих).

**Слежение включает сам `load_diagram`, а состояние стадий принадлежит диаграмме, а не окну** (боль Б1). Раньше `watch()` звал только список диаграмм и только для «обрабатываемых» статусов (`diagram_list.py`), поэтому у схемы, открытой в любом другом статусе, стадии не приезжали вовсе. Плюс пять кешей — `_last_stages`, `_filled_keys`, `_gate_blocked`, `_layout_gate`, `_project_code` — переживали смену диаграммы: кнопки, бусины и гейт НОВОЙ схемы решались стадиями предыдущей, а вкладки получали код проекта чужого проекта. Теперь `load_diagram` сбрасывает все пять и включает слежение (идемпотентно — множество uid; опрос сам снимется на финальном статусе без бегущих стадий).

**OCR polling** — отдельный таймер `_ocr_poll_timer` (3 сек), проверяет наличие артефакта `OCR_RESULT` через API. Это нужно, потому что OCR работает параллельно с graph/contours и не меняет DiagramStatus.

**Бусина OCR крутится, пока OCR РЕАЛЬНО бежит** (боль 1.4). В `_BEAD_DEFS` у неё стояли ВОСЕМЬ статусов «в процессе» подряд (`building_graph` … `contours_validated`), поэтому кружок «идёт распознавание» вертелся всю сборку графа и все контуры — независимо от того, запущен ли OCR вообще. Теперь «в процессе» ведёт живая строка `/stages` (`_ocr_stage_running`: `stage_type: ocr`, `status: running`), а статусный набор сужен до `OCR_PROCESSING` — мёртвого рудимента, который в прямом конвейере не присваивается нигде и достижим только откатом. Свежесть при остановленном опросе приносит тик `_ocr_poll_timer` (`_check_ocr_artifact` → `_on_stages_updated` → `_sync_ocr_bead`) — именно поэтому таймер живёт, даже когда артефакт ещё не появился. ⚠ Побочное следствие сужения, замеренное правкой: в `validated_graph` … `contours_validated` кнопка «Распознавание текста» больше не глухая (`_buttons_for_status` читает ту же таблицу). Дверь настоящая — `POST /api/ocr/{uid}/start` пускает `validated_graph` (`app/api/ocr.py:37,54`), — а пока OCR действительно бежит, кнопку по-прежнему глушит её строка стадии в `_update_buttons`.

**Гейт «Ручной правки» отпускает бусину сам** (боль 1.3). Ветка `gate.waiting` в `_apply_layout_gate` ставит бусину `edit_graph` в «в процессе», а при открытии двери чинилась ТОЛЬКО кнопка (`_restyle_button`) — кружок крутился до ручного «Обновить». Теперь ветка `allow` возвращает и бусину, по статусу и тем же путём, что `_update_beads`; красное (отказ отправки, упавшая стадия) не трогается — оно старше открытой двери.

### 3.4 Открытие/закрытие вкладок

Метод `_open_tab(tab_widget, tab_key)`:
1. Прячет header panel.
2. Добавляет tab_widget в layout.
3. Запускает AutoSave для вкладки.
4. Приостанавливает status polling.

Метод `_close_active_tab()`:
1. Спрашивает о несохранённом — через `confirm_discard_active_tab()` (см. ниже). Ответ «нет» возвращает управление, ничего не тронув.
2. Удаляет tab_widget из layout (вместе с ним останавливается AutoSave).
3. Показывает header panel.
4. Обновляет статус.
5. Только для вкладки труб — двойная страховка `_check_masks_completion()`.

**Вопрос о несохранённом — одна дверь на все пути ухода** (пункт 1.21 дороги). `confirm_discard_active_tab(action)` возвращает «можно ли трогать вкладку»; зовут его «← Назад» из вкладки и `MainWindow.closeEvent` (§2), и своё у них только слово `action` в тексте вопроса. Дверей было две, и они успели разойтись в четырёх клетках: текст; «Да» у вкладки без метода сохранения («← Назад» молча оставлял вкладку открытой — тупик без объяснения, окно закрывалось с записью в лог); след в логе на «Нет»; объяснение при отказе сохранения. Разрешено закрыться вкладке, которая сохраняться не умеет: тупик «не закрывается и не объясняет» дороже несохранённой вкладки, о которой оператора спросили.

Отвечает на «Да» первый найденный метод из `_TAB_SAVE_METHODS` = `_save_graph` → `_save_masks` → `_save_mask` → `_save_image` (у `OcrBindingTab` `_save_graph` — псевдоним `_save_binding`, у `FrameTab` свой `_save_image`). Вкладка **без** `has_unsaved_changes()` вопроса не поднимает вовсе — до пункта 1.21 такой была «Очистка рамки», и её работа уходила молча на обоих путях (§7.3).

**AutoSave гасится там, где вкладка умирает** — в `_remove_tab_widget()`, а не у вызывающих. Раньше `stop()` стояло в двух путях закрытия из пятнадцати (12 ведут в `_close_tab_and_restore_header`, 3 — в `_force_close_tab`), и это давало два дефекта сразу: «Отмена» на вопросе оставляла открытую вкладку с мёртвым таймером, а «Подтвердить» оставлял таймер крутиться на снесённом виджете.

**`_force_close_tab()` молчит законно.** Пути «← Назад в список» (`_on_back_to_list` → `cleanup()`) и «смена диаграммы» (`load_diagram`) сносят вкладку без вопроса, но жеста к ним при открытой вкладке нет: header с кнопкой «← Назад в список» спрятан, а список диаграмм лежит за ним. Инвариант заперт тестом `tests/ui/test_unsaved_question.py::test_header_back_is_unreachable_while_a_tab_is_open` — покраснеет он, значит жест появился и молчание стало дефектом.

⚠ Дрейф, замеченный пунктом 1.21 и не исправленный им: `tab.cleanup()` не зовёт НИКТО (ни один из 15 путей закрытия; замер §81). `BaseGraphTab.cleanup()` и `OcrBindingTab.cleanup()` гасят фоновую качку и сносят временный каталог — сейчас это не происходит. Прежняя редакция этого раздела обещала обратное («2. Вызывает `tab.cleanup()`»).

⭐ **Фоновый поток вкладки гасит САМ поток, а не её слоты** (пункт 1.x17). Раньше `quit()`
жил только в `_on_downloaded` / `_on_download_error` (у вкладок с распознаванием — в
`_cleanup_recog_thread`), то есть в слотах САМОЙ вкладки. Qt рвёт связи со слотами вместе
с разрушаемым получателем, а `cleanup()`, как сказано выше, не зовёт ни один путь закрытия —
значит уход из вкладки ДО конца загрузки оставлял бегущий `QThread` навсегда. Разрушение
БЕГУЩЕГО `QThread` — это abort процесса: `0xC0000409`, замер **4 из 4** в боевом пути
против **0 из 4**, когда загрузка успевала кончиться (`MEASUREMENTS §102а`). Для оператора
это «клиент падает при закрытии» после того, как он заглянул во вкладку и сразу вышел.
Теперь у каждой вкладки стоит связь `worker.finished/error → thread.quit`, получатель
которой — сам поток, поэтому она вкладку переживает.

⭐ **А сам рабочий объект уносит СЕБЯ, и уносит в СВОЁМ потоке** (пункт 1-46, замеры
`MEASUREMENTS §119а/§119б`). Связь `worker.finished/error → thread.quit` гасит ПОТОК, но
оставляла жить сам `ArtifactDownloader` (и `RecognizeWorker`): родителя Qt у него нет,
держал его только словарь вкладки, а вкладку разрушают. Замер: после «← Назад» и конца
потока C++-объект загрузчика ЖИВ у всех **четырёх** загрузочных вкладок (`isValid` истинно),
и его `thread()` — поток, которого больше нет. Снести такую сироту мог только питоний
сборщик и только ЧУЖИМ, главным потоком — то, чего Qt не разрешает делать с объектом,
живущим в другом потоке. Теперь у всех шести рабочих объектов (четыре загрузочных, два
распознавания) стоит `finished/error → worker.deleteLater`: `deleteLater()` из СВОЕГО
потока доигрывает его же цикл событий, пока он ещё жив. ⛔ Взводить снос ПОСЛЕ конца
потока бесполезно — замерено: `deleteLater()` для объекта в кончившемся потоке не
доставляется вовсе, доигрывать его больше нечем. Инвариант заперт набором
`tests/ui/test_tab_close_stops_threads.py::test_closing_tab_leaves_no_worker_in_a_dead_thread`
(четыре параметра, по вкладке на каждый).

Потоков **семь**, и это тоже замер, а не список (§102ж): четыре загрузочных
(`base_graph_tab`, `junction_tab`, `pipe_tab`, `ocr_binding_tab`), два распознавания текста
(`advanced_graph_tab`, `ocr_binding_tab`) и контурный `_ContourExtractWorker`
(`contour_tab.py:37`). У последнего связь идёт через `destroyed → worker.stop`: он подкласс
`QThread` со своим циклом опроса, `quit()` такой цикл не прерывает, а `closeEvent`,
в котором его гасили, при разрушении вкладки не поднимается вовсе. Его окно опасности —
до **600 с** опроса против 120 с у загрузочных.

⛔⭐ **НО ГАШЕНИЕ «КОГДА РАБОТНИК ДОРАБОТАЕТ» — ЭТО ПОЛОВИНА ЛЕЧЕНИЯ: НА МОЛЧАЩЕМ СЕРВЕРЕ
РАБОТНИК НЕ ДОРАБАТЫВАЕТ ВОВСЕ** (пункт 1-50, замеры `MEASUREMENTS §127`). Связь
`worker.finished/error → thread.quit` вкладку переживает, но срабатывает она только по концу
работы. Если оператор ушёл, пока сервер молчит, поток живёт дальше — и процесс, дошедший до
выхода с бегущим `QThread`, падает на его разрушении. Замер боевым жестом: «← Назад» при
молчащем сервере — **4 краха из 4** у каждой из четырёх загрузочных вкладок (`0xC0000409`),
контроль «сервер ответил» — **0 из 4**. Тот же класс у сборки `.prtx` рабочей области
(`cleanup()` её поток не упоминал вовсе): уход, закрытие клиента, оба вместе и даже выход
без жеста — **по 6 крахов из 6**.

⭐ Поэтому у каждого фонового потока клиента теперь ОДНА дверь —
`ui/services/thread_lifetime.hand_over(owner, thread, worker, name=…, uid=…)`, девять
носителей: семь вкладочных (выше), сборка `.prtx` (`diagram_workspace.py`) и проба лицензии
(`license_dialog.py`). Дверь делает две вещи: связывает `owner.destroyed` с просьбой
работнику остановиться (`stop()`) и гашением потока, и ставит поток на учёт, чтобы ВЫХОД
клиента (`ui/main.py` → `install_exit_guard`) его дождался. Ожидания в самой двери нет
сознательно: слот `destroyed` идёт в GUI-потоке, и `wait()` в нём заморозил бы окно ровно
в момент ухода оператора.

⛔ **Два очевидных лекарства проверены и НЕ работают:** удержать поток питоньей ссылкой —
**4 краха из 4**; дать ему родителя `QApplication` — **4 из 4**. Бегущий `QThread` не может
пережить выход процесса; лечит только то, что он кончается раньше. Отсюда прерываемость
работников там, где ожидание дорогое: `PrtxWorker` ждёт между опросами прерываемо (было до
15 минут, стало не дольше одного `POLL_SEC`), `ArtifactDownloader` не начинает оставшихся
заданий. ⚠ Граница названа: работник, стоящий в ОДНОМ HTTP-вызове (`RecognizeWorker` — до
200 с, `_ServerProbe` — 15 с), не прерывается ничем; для него выход ждёт свои 3 секунды и
уходит, НЕ разрушая объектов, оставив в логе строку с `uid` — иначе клиент падал бы ровно
там, где оператор уже ничего не может сделать.

⛔⭐ **КОРЕНЬ КРАХОВ БАЗОВОГО ГЕЙТА (`0xC0000005`) — СЦЕНА РЕДАКТОРА БЕЗ РОДИТЕЛЯ**
(пункт 1-46, замеры `MEASUREMENTS §119в–§119е`). `QGraphicsScene` во всех пяти редакторах
создаётся как `QGraphicsScene()` — без родителя Qt — и держится только питоньим полем
редактора. Разрушение вкладки её НЕ убивает: сцена переживает вкладку и умирает позже,
по воле сборщика мусора. А у сцены есть BSP-индекс (`QGraphicsSceneBspTreeIndex`,
приватный объект Qt), который на каждом изменении состава элементов заводит **НУЛЕВОЙ
таймер**. Тик такого таймера диспетчер доставляет по мёртвому получателю — нативный стек,
снятый на замороженном процессе: `QEventDispatcherWin32::event` →
`QCoreApplication::notifyInternal2` по освобождённой памяти; в части прогонов та же порча
всплывает раньше и даёт `0xC0000374` (порча кучи). Отсюда всё, что дорога наблюдала
сутками: платит ТОТ, КТО ПЕРВЫМ ПРОВЕРНЁТ ОЧЕРЕДЬ после разрушения настоящей вкладки,
имена «виноватых» тестов плавают, а узкий прогон зелен.

Корень подтверждён ВМЕШАТЕЛЬСТВОМ дважды, на паре наборов, дающей краш 4 из 4:
снять BSP-индекс (`NoIndex`) — **0 крахов из 4**; дать сцене родителя — **0 из 4**.
Лечение — родительство (`ui/tabs/scene_lifetime.py::adopt_editor_scene`, зовут пять
вкладок сразу после сборки редактора): сцена живёт ровно столько, сколько виджет,
который её показывает. `NoIndex` отвергнут замером цены: он делает поиск элемента
линейным, а сцены несут по две тысячи элементов и обслуживают мышь.

⚠ Граница названа честно: правка стоит у ВКЛАДОК, потому что `ui/editors/` в этот момент
правит другой пункт дороги. Редакторы, которые поднимают НАБОРЫ напрямую (мимо вкладки),
остаются со старым временем жизни сцены — поэтому `tests/ui` целиком крахи ещё даёт.
Полное лечение — одна строка `QGraphicsScene(self)` в каждом из пяти редакторов.

⚠ Остаток назван и адресован, а не забыт: оператор закрывает КЛИЕНТ, пока запрос висит
в сети. Оборвать `httpx` изнутри `quit()` нельзя — нужна кооперативная отмена, её адрес
**10-8**. Блокирующего `wait()` в `_remove_tab_widget` не будет и позже: боевой путь идёт
`download_artifact` → `_request_raw(timeout=120.0)` БЕЗ ретраев (`api_client.py:376-391`),
артефактов у вкладки несколько, и `wait()` на GUI-потоке дал бы заморозку клиента
до двух минут НА АРТЕФАКТ — цена хуже краха на выходе.

⛔ **Вкладка привязки OCR оставляла оператору шесть верхнеуровневых виджетов** (тот же
пункт). `kks_toolbar` и `diam_toolbar` создаются со всеми кнопками, но в раскладку не
попадают никогда — подвкладки убрал П3, `sub_tabs` в коде уже нет; плюс по две «скрытые
кнопки совместимости» внутри каждой панели. Виджет без родителя и без раскладки —
верхнеуровневый и живёт до конца процесса. Панелям дан родитель-вкладка и явный `hide()`,
кнопкам — родитель-панель; замер: было **6**, стало **0** (§102е).

**Команда о завершении валидации масок отправляется один раз на одно подтверждение** (пункт 1.20 дороги). Раньше шаг 7 стоял безусловно, а флаг `_pipe_confirmed` жил до конца сеанса с диаграммой — поэтому закрытие ЛЮБОЙ следующей вкладки слало `complete_mask_validation` заново, в том числе когда оператор на шаге 1 ОТКАЗАЛСЯ сохранять изменения. Пока сервер ещё не ушёл дальше `validated_masks`, такая повторная команда диспатчит скелетизацию второй раз (`app/api/validation.py:481-503`) — это UI-нога гонки двойной скелетизации; остальные две ноги (дыра `already_past` и гейт задачи) закрываются отдельно. Право доложить возвращает только новое подтверждение вкладки труб.

### 3.5 Rollback

Откат — **только по просьбе оператора**: кнопка уже пройденного этапа спрашивает «Откатить до …? Все последующие артефакты будут удалены» (`_on_button_click`) и лишь после «Да» зовёт `api_client.rollback_diagram()`.

Двух молчаливых откатов, которые здесь были, больше нет (пункт 1.3 дороги):

- при **открытии** диаграммы `_self_heal_stuck_stage()` откатывал застрявший `*ING`-статус **без preserve-флагов** — для «Проверки схемы» это сносило `graph_validated`, оба контурных артефакта, все четыре OCR-овых, холст и FXML (9 артефактов из 11);
- при **закрытии** вкладки без подтверждения `_rollback_if_validating()` откатывал статус из обоих путей закрытия; для «Очистки рамки» это уносило сохранённую оператором очистку вместе с `image_raw.png`.

Замер: откат не менял **ни одной** кнопки — набор доступных/пройденных совпадает у `*ING`-статуса и у стабильного (кнопку и так держит кликабельной поправка `_MANUAL_INPROGRESS` в `_update_buttons`). Различался только цвет бусины у `frame` и `junction`; теперь её красит такая же поправка в `_update_beads`, а `_note_unconfirmed_stage()` при открытии пишет в лог и в статусбар, что этап остался незавершённым.

## 5. Вкладки (Tabs)

### 5.1 BaseGraphTab

Файл: `ui/tabs/base_graph_tab.py`.

Абстрактный базовый класс вкладок редактора графа. Реализует template method:

1. **Download:** фоновая загрузка артефактов через общий `ArtifactDownloader`
   (`ui/services/artifact_downloader.py`) в `QThread`; что грузить — список `Job`
   из `_graph_jobs(want_canvas)`.
2. **Edit:** оператор работает в editor.
3. **Save:** `_save_graph()` → `api_client.upload_validated_graph()`.
4. **Confirm:** `confirmed` signal → workspace вызывает API complete endpoint.

Абстрактные методы: `_create_editor()`, `_setup_toolbar()`.

Signals: `confirmed()` — подтверждение завершения валидации (без аргументов; workspace получает uid из контекста вкладки).

Скачиваемые артефакты: `original_image` (обязательный), `graph_json` или `graph_validated` (с fallback), `coco_validated` (опциональный).

**Отказ загрузки сохранённой работы оператор видит** (пункт 1.23 дороги). Правило одно на все артефакты вкладки: **404 = сохранённого нет по-настоящему** (первый заход на этап) — фолбэк/пересборка законны и молчат; **любой другой отказ** (5xx, сеть, диск) — сохранённое могло лежать на сервере и просто не отдалось, поэтому вкладка предупреждает модалкой и пишет строку в лог клиента. Различение приезжает из загрузчика полем `Job.failure_key` (`ui/services/artifact_downloader.py`), тем же механизмом, что и у `contours_validated`:

| артефакт | флаг | что говорит модалка |
|---|---|---|
| `graph_validated` → фолбэк `graph_json` | `saved_graph_download_failed` | «Сохранённый граф не загружен» — текст по АДРЕСАТУ записи (см. ниже) |
| `graph_canvas` (только WYSIWYG) | `canvas_download_failed` | «Холст не загружен» — холст пересобран заново, сохранение затрёт серверный холст |

Раньше обе ветки молчали: фолбэк графа брался без разбора причины, а предупреждение о пересборке холста стояло внутри `if saved:` и при неудачной загрузке не показывалось вовсе — тихая пересборка плюс первый же Ctrl+S затирали ручную раскладку на сервере (семья 1.5: на сервер уходит то, что считает дёрти-флаг).

⛔ **Предупреждение называет тот артефакт, который затрёт сохранение** (блок 5
линии «Ручная правка + FXML», п. 5.1, 2026-08-25). Текст был один на обе вкладки
и в «Ручной правке» врал дважды: обещал затереть сохранённый граф — хотя
`_save_graph` при `_canvas_mode` шлёт `upload_canvas_graph`, — и объявлял
открытым ИСХОДНЫЙ граф, тогда как источник не прочитан, `_canvas_is_stale`
отдаёт `False` и холст оператора остаётся ему как есть (это же меряет
`test_saved_graph_5xx_keeps_the_fresh_canvas`). Адресата выбирает `_canvas_mode`,
поэтому и предупреждение переехало ПОСЛЕ развилки холста
(`BaseGraphTab._warn_saved_graph_not_loaded`): в холстовой вкладке речь о
холсте «Ручной правки», в вкладках оригинальных координат — прежний текст про
`graph_validated`. Заперто обеими полярностями в
`tests/ui/test_download_failure_is_visible.py`.

**Предупреждение МЕШАЕТ записи** (пункт 1.x9 дороги). Одного «оператор видит» мало: 1.23 закрыл видимость отказа, а запись оставалась свободной — первый же save затирал на сервере то, что прочитать не удалось. Теперь артефакт с неизвестным серверным состоянием попадает в `BaseGraphTab._unreadable_on_server`, и `_save_graph` до записи спрашивает подтверждение (`_confirm_blind_overwrite`):

- запрет **адресный** — под ним ровно тот артефакт, в который вкладка пишет (`graph_canvas` в режиме холста, иначе `graph_validated`); отказ соседа запись не запирает;
- «да» снимает запрет насовсем (решение принял оператор), «нет» отменяет сохранение и возвращает вопрос при следующей попытке; обе ветки пишут строку в лог клиента;
- 404 запрета не ставит: сохранённого законно нет, затирать нечего;
- ⛔ **дверь ОДНА на все четыре пишущие вкладки** (пункт 1-41): `_confirm_blind_overwrite` и реестр `_unreadable_on_server` живут в `ui/tabs/blind_overwrite.py` (`BlindOverwriteGuard`), а вкладка объявляет своё — `_BLIND_WRITE_WARNING` (о чём предупредить), `_UNREADABLE_FLAGS` (какой `Job.failure_key` что означает) и `_BLIND_WRITE_ARTIFACTS` (во что пишет её метод сохранения). До этого запрет был реализован ДВАЖДЫ — здесь и в `OcrBindingTab`, — то есть готовое расхождение того же класса, что 1-18 нашёл у дверей вопроса о несохранённом (там две двери разошлись в четырёх клетках из четырёх);
- запрет стоит в `_save_graph`, потому что через него идут все боевые входы на сервер — кнопка 💾, «Подтвердить» и автосохранение (раз в 120 с, включено по умолчанию). ⛔ **Автосохранение вопроса не задаёт** (пункт 1-38, §11.3): тик отказывается от записи и говорит об этом строкой, а запрет оставляет взведённым — иначе фоновое «да» снимало бы защиту без оператора. Ctrl+S с пункта 1.19 дороги идёт туда же: он **жмёт кнопку 💾** (см. §12.1), то есть попадает под тот же запрет, а не мимо него. До 1.19 хоткей открывал локальный `QFileDialog` и сервера не касался вовсе.

**Непрочитанный источник не старит холст** (тот же пункт). При отказе `graph_validated` вкладка получает фолбэк `graph_json`, а холст сверялся по нему — свежий холст объявлялся устаревшим и пересобирался, и модалка «Схема изменилась» называла причину, которой не было. Теперь `_canvas_is_stale(..., download_failed=True)` отвечает «не устарел» (то же различение, что у `_canvas_contours_stale` из 0.5): судить нечем — холст остаётся оператору. Из того же соображения при непрочитанном источнике **не выполняется импорт подписей** на холст: `import_text` при источнике без `text_blocks` чистит холст досуха, а фолбэк — граф до OCR, подписей в нём нет по определению.

⛔ **Кнопки вопросов — русские, и вопрос один на двоих** (блок 5, п. 5.3,
2026-08-25). `QTranslator` в проекте не установлен, поэтому Qt рисует
стандартные подписи латиницей: замер на боевом PySide6 дал `['OK']` для
однокнопочных модалок и `['Cancel', '&Yes']` для вопросов. Переводить пришлось
только вторые — «OK» и в русском интерфейсе «OK», — а вопросов у графовых
вкладок два: запрет слепой перезаписи и «Подтвердить» (`_on_confirm`). Оба
собираются одной дверью `BlindOverwriteGuard._ask_yes_cancel` своими кнопками
(«Да» / «Отмена», дефолт — «Отмена»); прецедент своей сборки — диалог конфликта
диаметров `ocr_binding_editor.py`. ⚠ Дверь одна нарочно: две двери одного
вопроса на этой дороге уже расходились в четырёх клетках из четырёх (1-18).
⚠ Наборы, подменявшие статический `QMessageBox.question`, теперь подменяют
`_ask_yes_cancel` — иначе живой модальный диалог подвесит прогон.
⛔ Вопрос о несохранённом (`DiagramWorkspace.confirm_discard_active_tab`, §3.4)
под эту правку НЕ попал — он вне зоны блока 5, кнопки там прежние.

**Отказ ЛОКАЛЬНОГО диска уводит вкладку в ошибку** (пункт 1.x12 дороги). У обоих необязательных заданий (`coco_validated`, `pipe_mask`) стоит `swallow=(APIError,)` — то же правило 0.5, что и в §5.1: отказ **сервера** терпим (артефакта может законно не быть — 404 и 5xx глотаются молча), отказ **локального диска** — нет. Обратно на сервер эти артефакты не уходят, поэтому цена тише, чем у соседних вкладок: до 1.x12 вкладка молча открывалась с дефолтной шириной кисти вместо медианной — тем же симптомом, что и в дефекте 1.x3, но по другой причине.

**Отказ ЧТЕНИЯ сохранённой маски запирает запись** (пункт 1-41 дороги). Цепочка `pipe_mask_validated` → `skeleton_mask` брала фолбэк молча: при 5xx оператору открывали СЫРОЙ скелет сборщика, а `_save_mask` писал его обратно в `pipe_mask_validated` — сохранённая работа исчезала. Теперь у цепочки `failure_key="pipe_mask_download_failed"`, вкладка предупреждает модалкой «Сохранённая маска труб не загружена» и до записи спрашивает подтверждение общей дверью `_confirm_blind_overwrite` (§5.1). Различение прежнее: **404 = сохранённого законно нет** (первый заход) — молчит; любой другой отказ = могло лежать. ⚠ `coco_validated` под запрет НЕ попал осознанно (`silent_ok` у задания): `upload_updated_nodes` идёт только при `has_coco_changes`, а `save_coco` без прочитанного `coco_full_data` отдаёт `False` — запись гейтирована чтением, слепой перезаписи здесь быть не может.

**Стартовая ширина кисти = медианная толщина труб**, посчитанная по маске сегментации (`_estimate_median_thickness`, distanceTransform по скелету), с зажимом в диапазон слайдера 2..12; маски сегментации нет — остаётся дефолт 4 px. До пункта 1.x3 дороги вкладка просила тип `segmentation_mask`, которого нет в `ArtifactType`: эндпоинт `GET /{uid}/download/{type}` валидирует тип **до** поиска артефакта (`app/api/diagrams.py:369-376`) и отвечал 400, необязательное задание его глотало — медиана не считалась ни разу, и ширина всегда была дефолтной вопреки тултипу. ⛔ Тип артефакта в списке заданий вкладки обязан быть значением `ArtifactType`; подставной сервер в тестах щедрее боевого, поэтому это сторожится сверкой с самим перечислением (`tests/ui/test_pipe_tab_artifact_types.py`).

### 5.3 JunctionTab

Валидация масок junction/bridge. Использует `SquareMaskEditor` (см. §7.2).

Скачивает: original_image, skeleton, skeleton_mask, junction_mask + bridge_mask (validated или raw), coco_validated, центры квадратов (`junction_points_validated` → `junction_points`, опционально — старый сервер типов не знает).

Кнопки toolbar: класс (Junction белая / Bridge красная, клавиши 1/2), размер квадрата-**кисти** (QSlider 3..15), **«Размер объектов» (QSpinBox 3..100) + «Применить размер»**, Undo, Сохранить, Подтвердить.

**Размер кисти ≠ размер объектов.** Слайдер задаёт квадрат, который ставится по Ctrl+ЛКМ. Спинбокс с кнопкой меняет **реальный** размер уже существующих перекрёстков/мостов (сжатие/расширение относительно центра) и потолок 15 не наследует: расширение может требовать больше. Правило: есть выделение (Shift+протяжка) — меняются выделенные пятна; выделения нет — все пятна текущего класса, с подтверждением.

Сохранение отправляет на сервер обе маски **и центры квадратов** (`points_validated.json`). Без центров операция изменения размера ломала бы себя при переоткрытии вкладки: экстрактор с дефолтным окном 15 px не находит окна в квадратах, ужатых до меньшего, и слипшаяся пара сворачивается в один центр.

**Отказ ЛОКАЛЬНОГО диска уводит вкладку в ошибку** (пункт 1.x12 дороги). У всех четырёх необязательных заданий (`bridge_mask_validated`, `skeleton_final`, `coco_validated`, `junction_points_validated`) стоит `swallow=(APIError,)` — то же правило 0.5, что и в §5.1: отказ **сервера** терпим (404 и 5xx глотаются молча), отказ **локального диска** — нет. Цена молчания здесь замерена сценарием, а не выведена: тихо потерянный `bridge_mask_validated` → редактор берёт **пустую** маску мостов (`load_images(mask2_path="")`), а `_save_masks` шлёт её на сервер безусловно — из 1200 белых пикселей оператора оставалось **0**; тихо потерянные центры → `_upload_points` подменяет применённый оператором размер машинным дефолтом (20 → 15), и при следующем открытии экстрактор не разбирает ужатые квадраты. Путь достижим и без оператора: автосохранение зовёт тот же `_save_masks` по таймеру (§11.3).

**Отказ ЗАПИСИ центров оператор видит** (пункт 1.x14 дороги). Тот же дефект семьи, но на другом пути: `_upload_points` глотал `except Exception` целиком, поэтому неудавшаяся отправка центров не выходила наружу — `_save_masks` ставил `_saved = True` и писал «Маски перекрёстков и мостов сохранены». Замер: во **всех** классах отказа (локальный диск, 400 старого сервера, 5xx, обрыв связи) на сервере оставался прежний размер 20 против применённых оператором 24, модалки не было ни в одном, а взведённый `_saved` гасил `has_unsaved_changes()` — вкладка закрывалась без вопроса, и работа исчезала без следа в UI.

Граница у **чтения** проходит по `APIError` потому, что там он мог означать «артефакта законно нет» (404). У **записи** такого прочтения нет ни у одного класса: и старый сервер, не знающий типа, и 5xx, и обрыв, и диск означают одно — работа оператора до сервера не доехала. Поэтому `_upload_points` возвращает `bool`, а `_save_masks` при неудаче показывает модалку «Центры не сохранены» (с ценой: применённый размер будет заменён машинным), пишет строку в лог и возвращает `False`, не взводя `_saved`. Маски, которые уже записались, **не откатываются** — оператор теряет ровно центры, и ровно про них ему и говорят; общий обработчик сказал бы «не удалось сохранить junction маски», а это была бы новая неправда.

⚠ Следствие, названное прямо: неудавшаяся запись центров **не даёт подтвердить вкладку** — `_on_confirm` идёт через тот же `_save_masks`. Это осознанно: сохранённой вкладка при непрошедшей записи не считается, значит и подтверждать нечего. Обратная сторона — сервер, который не знает типа `junction_points_validated` (развёрнут раньше 2026-07-28), запирает этап до обновления сервера; на совпадающих версиях клиента и сервера такого отказа нет.

**Отказ ЧТЕНИЯ запирает запись у всех трёх записываемых артефактов** (пункт 1-41 дороги). 1.x12 подвинул границу по ДИСКУ и остаток назвал прямо: сохранённые мосты могли лежать на сервере, и вкладка откроется без них так же молча, как при 404. Задания вкладки `failure_key` не несли вовсе, поэтому 5xx и 404 были неразличимы у **junction_mask_validated** (цепочка → сырая маска сборщика), **bridge_mask_validated** (→ сырая или пустая) и **junction_points_validated** (→ машинные центры). Теперь каждый несёт свой `failure_key`, вкладка предупреждает модалкой и до записи спрашивает подтверждение общей дверью `_confirm_blind_overwrite` (§5.1). ⚠ `skeleton` и `coco_validated` под запрет не попали осознанно (`silent_ok` у заданий): обратно на сервер эта вкладка их не пишет.

**«Файл лёг, но не читается» — отказ того же смысла** (тот же пункт). Семья закрывала отказы сети, диска и сервера, а порчу СОДЕРЖИМОГО скачанного — нет: `_load_points` ловил `(OSError, ValueError)` строкой в лог, `ensure_points` доопределял центры машинным дефолтом, и `_upload_points` отправлял их обратно — та же цена, что у потерянных центров (20 → 15). Теперь нечитаемый `points.json` поднимает тот же флаг, что и неотдавшийся.

При подтверждении вкладки, если у диаграммы уже есть сохранённый холст «Ручной правки», появляется предупреждение: пересборка графа уничтожит ручную раскладку WYSIWYG (холст пересобирается с нуля по `source_sha`). Поведение конвейера при этом не меняется — оператор только информируется.

### 5.5 AdvancedGraphTab

Вторая фаза валидации графа. Использует `AdvancedGraphEditor` (см. §6.3).

Это вкладка «Ручная правка» — единственная работает в холсте 1920x1080 (WYSIWYG, `USE_CANVAS = True`). Особенности холста:

- ⛔ **Холст либо ЕСТЬ, либо вкладки нет — аварийной пересборки больше не существует** (блок 8 линии «Ручная правка + FXML», решения Максима №8/№9, 2026-08-26). Прежде вкладка в четырёх ветках сразу (холста нет · холст устарел · холст не скачался · любой сбой подготовки) молча собирала холст локальным `pretransform`-ом **без раскладки** и открывала его как рабочий: оператор правил недосчитанное, а настоящая раскладка, поставленная закрытием «Контуров», ложилась рядом и его правки теряла. Теперь `canvas_verdict()` (`ui/tabs/base_graph_tab.py`) отвечает одним из пяти слов, и редактор создаётся только на `ready`:

  | вердикт | что видит оператор вместо редактора |
  |---|---|
  | `ready` | холст свеж — обычная вкладка |
  | `missing` / `stale`, задача раскладки **бежит** (стадия `layout` в `pending`/`running`) | «Раскладка пересчитывается» — экран ждёт и **отпирается сам** по готовности, перечитывая холст |
  | `missing` / `stale`, задачи **нет** | дверь: «вернитесь в „Контуры“ и нажмите „Подтвердить“ — это запустит пересчёт» (`POST /contours/{uid}/complete` диспатчит раскладку всегда) |
  | `download_failed` (5xx, сеть) | «Холст не загружен» + «Повторить»: это **не** «холста нет», на сервере лежит ручная раскладка |
  | `broken` (скачался, но не готовится) | то же с причиной; сырой граф «как есть» больше не подставляется |

  Экран ожидания **перестаёт обещать** «схема откроется сама» после `WAIT_LIMIT_S` от `started_at`: зависшую насмерть задачу сервер сам не закроет (`plan_dispatch` → `ALREADY_RUNNING`), и обещание без срока годности — та же ложь, что «пересчитывается» без задачи. Пока экран поднят, кнопки 💾 и «Подтвердить» выключены (писать некому — редактора нет) и им возвращаются исходные подсказки при открытии холста; запрет слепой перезаписи снимается вместе с причиной: удачное перечитывание чистит `_unreadable_on_server`. Неудачный повтор экран не сносит, а поднимает заново — иначе вкладка становится тупиком без кнопки. Пустой список стадий (его отдаёт `get_stages` при отказе сервера) экран **не двигает**: переход «задача была → задачи нет» требует положительного знания, иначе один сбойный тик перезагружал бы все артефакты. Дверь ожидания живёт опросом: вкладка просит воркспейс вернуть слежение (`layout_watch_requested` → `DiagramWorkspace._on_tab_wants_stages`), потому что `_open_tab` его снимает, и слушает `stages_updated`. Перечитывание идёт по ПЕРЕХОДУ «задача была → задачи нет», а не по факту `completed`: холст умеет родиться протухшим и при завершённой задаче (угол `ALREADY_RUNNING` диспетчера), и реакция на «completed» закольцевала бы экран.
- **Замок авто-инструментов** (`_apply_layout_lock`, зовётся из `_on_editor_ready`). Работает В ОБЕ СТОРОНЫ, по одной метке `canvas_state.has_layout`:
  - `layout_applied: true` (продукт авто-раскладки) — выключены «Оптимизировать» и «Оптимизировать все» (замер §1.1 EDITOR_AFTER_LAYOUT: поверх раскладки они дают регрессию);
  - `layout_applied: false` или метки нет (фолбэк- и legacy-холсты) — выключено **«Авто-выравнивание»** (пункт 4.1 линии «Ручная правка + FXML», 2026-08-25). До этого за одной кнопкой стояло ДВА движка: на разложенном холсте — Э4-сглаживание, иначе — прежний `auto_fix_graph` без единой проверки коллизий и без отката хода. Ветка была живой в обычном цикле: холст с `layout_applied: false` мог быть сохранён на сервер прошлой сессией и грузится как актуальный (этот путь жив и после блока 8 — потому замок и остаётся обязательным; вторая половина основания, except-хвост загрузки, блоком 8 снята: сырой граф больше не подставляется). Тултип называет причину и дверь («Контуры» → «Подтвердить» запустит пересчёт); тот же гейт стоит и внутри `_auto_fix`, потому что метод вкладки зовут не только кликом.
  У каждой запертой кнопки исходная подсказка сохраняется в `_pre_lock_tooltip` и возвращается при отпускании.
- **«Авто-выравнивание» не выглядит зависшим** (пункт 4.4, 2026-08-25). Сглаживание блокирующее — по 20 холстам корпуса медиана 2.8 с, худший случай 6.6 с (`MEASUREMENTS §MEFX4Bб`) — и в фоновый поток НЕ выносится: движок мутирует живую модель и зовёт Qt-колбэки (`route_fn` трогает `QGraphicsItem`, снапшот — `_redraw_all`). Поэтому на время прогона ставится `QApplication.setOverrideCursor(Qt.WaitCursor)` и строка «Сглаживание…» (синхронный `repaint()` одного ярлыка; `processEvents()` в клиенте не зовётся нигде). Курсор снимается своим вложенным `finally` — раньше отчёта об отказе, иначе модалка открывалась бы под песочными часами. По окончании к сводке ходов дописываются **вёдра отказа** (`edit_smooth.REFUSAL_KINDS`: «нет кандидата» / «сверх бюджета» / «лестница исчерпана») — оператор видит не только «осталось N», но и почему; перечень читается из движка, пустые вёдра в строку не попадают.
- **Очаги остатка раскладки** — вырезано 2026-08-02: кнопка «Очаги (N)», маркеры (`ResidualLayerMixin`) и панель (`ResidualPanel`) удалены из UI; артефакт `residual_defects.json` — легаси (см. DATA_FORMATS.md).
- **Починка посадки концов.** При открытии актуального холста концы рёбер пересаживаются каноном `seating` (`ui/tabs/base_graph_tab.py::_reseat_canvas_endpoints`, канон — `modules/graph/core/pretransform.seat_edge_endpoints`); правится локальная temp-копия, на сервер починка уезжает обычным сохранением оператора. Конец, закреплённый пином (см. §6.3), — вне канона: пин восстанавливается последним словом прогона.
- **Миграция легаси-намерений (до 2026-08-03).** Там же, в `_reseat_canvas_endpoints`, старые хранилища ручных правок один раз переводятся в пины: `node['_ports']` с владельцем-парой → пины живых рёбер пары (записи без владельца, сироты без ребра и коннекторы — дроп с логом), `_manual_route` → пины обоих не-коннекторных концов (флаг снимается), `_auto_route` стирается — серверная подпись `avoid_router` продолжает писаться в свежих холстах, но редактором не читается (инертна).

**Отказ инструмента оператор видит отчётом, а не строкой** (пункт ДН3 дороги). Падение «Авто-выравнивания» печатало трассировку в `sys.stderr`, которого в собранном `.exe` нет (`console=False`), а логгер в `except` не звался вовсе: прирост `client.log` на отказе был 0 байт (замер `MEASUREMENTS §96`), и оператору доставалась одна строка `QMessageBox` — единственный след ошибки терялся. Теперь отказ (1) уходит в лог клиента с трассировкой и `uid` (§11.5), (2) открывает `ErrorReportDialog` (§9.4) с приложенным ХОЛСТОМ и полем заметки, (3) возвращает фокус редактору: строка `setFocus()` переехала из конца `try` в `finally`, потому что после отказа холст уже изменён, шаг отмены открыт (пункт 1.1) — и Ctrl+Z оператору нужен тем более.

### 5.7 OcrBindingTab

Файл: `ui/tabs/ocr_binding_tab.py`.

Привязка OCR текста к узлам/рёбрам графа. Использует `OcrBindingEditor` (см. §8).

Архитектура v2 — 3 подвкладки:
1. **KKS** — коррекция и привязка KKS-кодов к equipment nodes.
2. **Диаметр** — привязка диаметров к рёбрам.
3. **Другое** — прочие блоки + финальное подтверждение.

Классификация OCR-блоков запускается автоматически при загрузке. Цвета боксов по confidence: зелёный (high), жёлтый (medium), оранжевый (low).

**Отказ загрузки сохранённого графа виден и здесь** (пункт 1.x8 дороги). Цепочка `graph_validated` → `graph_json` несёт `failure_key="saved_graph_download_failed"` по тому же правилу, что и в §5.1: 404 = сохранённого законно нет (первый заход) — фолбэк молчит; любой другой отказ (5xx, сеть, диск) — модалка «Сохранённый граф не загружен» плюс строка в лог клиента. Цена молчания здесь такая же: `_save_binding` кладёт `_graph_data` обратно в `graph_validated`, поэтому первое же «Сохранить» — или тик автосохранения, который зовёт `_save_binding` напрямую (§11.3) — затирает сохранённую работу оператора исходным графом сборщика.

**Отказ ЛОКАЛЬНОГО диска уводит вкладку в ошибку** (пункт 1.x10 дороги). У всех необязательных заданий вкладки стоит `swallow=(APIError,)` — то же правило 0.5, что и в §5.1, и до 1.x10 оно здесь было потеряно (стоял дефолтный `swallow=(Exception,)`). Граница проходит по `APIError`: `APIClient._request_raw` заворачивает в него и коды HTTP, и сетевые сбои, а запись скачанного в файл лежит **за** этой обёрткой — значит не-`APIError` означает «скачанное не легло на диск». Цена молчания замерена сценарием, а не выведена: `_save_binding` пишет привязки обратно **безусловно**, поэтому вкладка, открытая без них, стирала сохранённую работу оператора первым же сохранением — из 2 привязок на сервере оставалось 0, в том числе по тику автосохранения (§11.3), без участия оператора.

**Отказ СЕРВЕРА у привязок оператор тоже видит** (пункт 1.x12 дороги). `swallow` его не берёт по построению: 5xx **завёрнут** в `APIError`, поэтому вкладка открывалась пустой так же молча, как при законном 404. Лечит это `failure_key="binding_download_failed"` — тот же механизм, что и у графа в §5.1, и то же различение: 404 = привязок законно нет (первый заход), любой другой отказ сервера = они **могли** лежать → модалка «Сохранённые привязки не загружены» плюс строка в лог клиента.

**Предупреждение МЕШАЕТ записи и здесь** (пункт 1.x14 дороги). Запрет слепой перезаписи ввёл 1.x9, но жил он в `BaseGraphTab._save_graph`, а эта вкладка от базового класса не наследуется (`OcrBindingTab(AppearanceMixin, QWidget)`) — то есть повторяла ровно тот дефект, который 1.x9 закрыл у графовых вкладок: оператор видел предупреждение, а «Сохранить» всё равно затирало серверную копию. Теперь артефакт с неизвестным серверным состоянием попадает в `OcrBindingTab._unreadable_on_server`, и `_save_binding` до записи спрашивает подтверждение (`_confirm_blind_overwrite`):

- запрет стоит на **оба** артефакта, в которые пишет метод: привязки (`save_ocr_binding`) и граф (`upload_validated_graph`). Дверь, закрытая только со стороны привязок, оставила бы вторую половину настежь;
- «да» снимает запрет насовсем (решение принял оператор), «нет» отменяет сохранение целиком и возвращает вопрос при следующей попытке; обе ветки пишут строку в лог клиента;
- разрешение засчитывается, только если разрешены **все** спрошенные артефакты: «да» первому при «нет» второму ничего не записало, значит и разрешения оператор не давал;
- 404 запрета не ставит: сохранённого законно нет, затирать нечего;
- запрет стоит в `_save_binding`, потому что через него идут все три боевых входа на сервер — кнопка 💾, «Подтвердить» и автосохранение (`_SAVE_METHODS["OcrBindingTab"]`, раз в 120 с, включено по умолчанию, §11.3). ⛔ **Автосохранение вопроса не задаёт** (пункт 1-38, §11.3): тик отказывается от записи и говорит об этом строкой, а запрет оставляет взведённым.

**Третий записываемый артефакт — `ocr_validation`** (пункт 1-41 дороги). 1.x9 и 1.x14 закрыли запрет по ДВУМ артефактам, а `_save_binding` пишет ТРИ: шагом 6 на сервер уходят подтверждения блоков. Задание `ocr_validation` `failure_key` не несло, то есть 5xx и 404 были неразличимы, и оператор, поработавший в режиме валидации хотя бы над одним блоком, стирал этим свои подтверждения прошлого захода. Теперь у задания `failure_key="ocr_validation_download_failed"`, вкладка предупреждает модалкой «Сохранённые подтверждения не загружены», а `_save_binding` спрашивает про все три артефакта сразу. ⛔ Тот же флаг поднимает и **разбор скачанного файла**: `ocr_validation.json` разбирается в СВОЁМ `try`, мимо общего обработчика загрузки, и «файл лёг, но не читается» уходило одной строкой в лог — класс отказа, который семья не закрывала ни на одном слое.

**«⏳ OCR в процессе» больше не показывается на отказе, который ожиданием не лечится** (тот же пункт). `_on_download_error` повторяет загрузку 10 раз по 5 с — для «OCR ещё не готов» это правда (артефакта пока нет, сервер отвечает 404, следующая попытка его застанет), а для отказа локального диска это была ложь о работе почти на минуту, после которой оператор всё равно получал «❌ Ошибка». Граница та же, что у `swallow`: класс отказа приезжает во вкладку полем `ArtifactDownloader.last_error`, и не-`APIError` показывается сразу.

**«В процессе» осталось ровно у 404** (пункт 1.x14 дороги). 1.x12 закрыл только не-`APIError`, а 5xx у обязательного артефакта продолжал давать те же 10 попыток с тем же текстом — то есть оператор видел ложь о работе OCR все ~50 секунд ретраев. Правда про ожидание есть у одного кода: 404 = артефакта **пока** нет, следующая попытка его застанет. Сервер, который ответил и отказал (5xx, обрыв связи, отказ прав), про работу OCR не говорит ничего, поэтому вкладка называет причину: «⚠ Сервер не отдаёт данные: …, повтор через 5 с (попытка N/10)» плюс строка в лог клиента. ⚠ Повтор при этом **оставлен** — шлюзовой отказ и обрыв связи со следующей попытки проходят; правка трогает текст, а не ожидание.

## 6. Редакторы (Editors)

### 6.1 BaseGraphEditor

Файл: `ui/editors/base_graph_editor.py`.

Базовый класс — `QGraphicsView` с рендерингом графа P&ID поверх изображения.

**Данные:** `GraphDataModel` (nodes, edges, coco_annotations) + `UndoManager` (стек команд).

**Рендеринг:**
- Изображение → `QGraphicsPixmapItem` на сцене.
- Узлы → `QGraphicsEllipseItem` (equipment: синий R=6, connector: зелёный R=8 — connector крупнее для визуальной заметности на ребре, isolated: красный).
- Рёбра → `QGraphicsPathItem` (polyline через waypoints).
- Текст → `QGraphicsSimpleTextItem` (KKS labels, diameter labels).
- Подсветка сторон с подключением → `QGraphicsPathItem` (`side_items[node_id]`, z=2.5 — поверх рамки узла, под маркером-центроидом).

**Два радиуса коннектора разведены намеренно.** `CONNECTOR_MARKER_RADIUS` — геометрический: виртуальный bbox коннектора (`_get_node_bbox`), от него зависят посадка рёбер (`source_point`/`target_point` → FXML), сторона ребра и геометрия ОКР-привязки. `CONNECTOR_DRAW_RADIUS` — нарисованный, его и крутит ползунок «размер коннекторов». Дефолты равны, поэтому вид по умолчанию не меняется. То же зеркально сделано в `OcrBindingEditor` (`NODE_RADIUS` / `NODE_DRAW_RADIUS`).

**Подсветка стороны блока, где есть подключение** (по умолчанию включена, переключатель и цвет — в шестерёнке): участок границы длиной `SIDE_MARK_LEN` вокруг точки входа трубы, единый алгоритм для боксов и полигонов (`graph_geometry.boundary_mark_points`). Бокс обрезается по грани — у мелкого бокса штрих иначе завернул бы за угол; контур проходится через вершины. Точка входа берётся из `_visual_edge_ends`, а форма — из `_node_has_polygon`: важно брать то, что **нарисовано**, а не сырые данные (в холсте у скинового узла контур не рисуется, форма = bbox). Участков столько, сколько разных точек входа; совпавшие схлопываются. Обновление — хуком в `create_edge_item` / `_update_edge_path` / `remove_edge_item`, через которые проходят все точечные пересчёты рёбер.

**Навигация:** Ctrl+Wheel = zoom, ЛКМ drag = pan (ScrollHandDrag).

**Hit testing:** `find_node_at(x, y)` — поиск узла в радиусе `CLICK_THRESHOLD=20`. `find_nearest_edge(x, y, threshold)` — ближайшее ребро.

**Mode system:** паттерн ModeHandler (см. CODING_GUIDE.md §3.2). Каждый режим (`add_edge`, `delete_edge`, `drag_node`, ...) — отдельный handler, зарегистрированный через `register_mode()`. Событие Ctrl+Click делегируется текущему handler.

**Connection points:** `get_connection_point(node_id, target_x, target_y)` — вычисляет точку на контуре узла (bbox или polygon), ближайшую к целевой точке. Поддерживает rect, polygon и circle.

**Превью панели «Размеры» (Р9, 2026-08-19).** Бегунок/спинбоксы зовут `preview_resize`, и он меняет **модель**, а не только сцену — поэтому у превью есть базлайн (`_capture_resize_base`: геометрия набора, снимок модели и **пины инцидентных рёбер**) и четыре выхода. «Применить» (`apply_resize`) фиксирует превью `SnapshotCommand` от базлайна — Ctrl+Z возвращает и рамки, и пины. Смена набора и выход из режима (Esc или кнопка режима) считаются брошенным превью: `_revert_resize_preview` возвращает набор к базлайну и пишет строку в лог клиента. Остальные два выхода — запись на сервер и команда-на-месте — ниже отдельными абзацами; «любого другого исхода» тут нет, каждый путь снимает превью сам. Пины входят в базлайн обязательно: `rescale_edge_pins` домножает `dx/dy` на месте, и без возврата к исходным каждый тик бегунка множит уже домноженное (замер `MEASUREMENTS §48`: `dx` 10.0 → 45.0 → 202.5 за два тика одним и тем же 90×90, после «Применить» — 911.25 при полуширине узла 45).

⛔ **Живое превью не уходит на сервер (Р13, 2026-08-19).** Третий выход из превью — сохранение: `BaseGraphTab._save_graph` зовёт `editor.drop_uncommitted_preview()` **до** сериализации, и `AdvancedGraphEditor` снимает превью тем же `_revert_resize_preview` (панель при этом не сбрасывается — иначе набранные оператором ширина/высота затёрлись бы медианами). Так путь записи согласован с дёрти-флагом: на сервер уходит ровно то, что флаг считает (см. §11.3). До этого запись шла от модели КАК ЕСТЬ, и после 1.4 сервер расходился с моделью — замер `MEASUREMENTS §50`: «превью → Сохранить → выход» оставлял на сервере `node_11` = `[-10.0, 188.0, 80.0, 278.0]` при исходных `[25, 215, 45, 251]` в модели.

⛔ **Живое превью не вваривается в команду (доработка 1.4 по ревизии связки, 2026-08-19).** Четвёртый выход: команда-на-месте, нажатая поверх живого превью. `SnapshotCommand._before` снимается с модели КАК ЕСТЬ, то есть вместе с превью, — и оно становится НЕОТКАТЫВАЕМЫМ: `undo_mgr.revision` растёт, базлайн объявляется протухшим, а лечение «протух → бросить без отката» превью уже не трогает. Замер `MEASUREMENTS §52` до правки: «превью 90×90 → «Авто-выравнивание» → Ctrl+Z» возвращал `node_11` = `[-10.0, 188.0, 80.0, 278.0]` вместо исходных `[25, 215, 45, 251]`, и то же уезжало на сервер; то же самое давали «Оптимизировать все» и «Удалить выделенное». Поздним откатом это не лечится — `_before` уже отравлен. Поэтому такие команды зовут `drop_uncommitted_preview()` **до** снятия своей точки возврата: `smooth_canvas`, `auto_fix`, `optimize_all_edges`, `batch_delete`. Кнопка, не построившая точки возврата (`batch_delete` без выделения), превью НЕ снимает: вваривать нечего.

⛔ **Четырьмя кнопками список не исчерпывается — перебор ведётся по вопросу «достижимо ли при `_current_mode == 'resize_objects'`», а не «в чьём это mode handler» (вторая доработка 1.4 по ревизии связки, 2026-08-19).** Первый свип шёл по handler-ам и потому не увидел трёх путей, которые живут ВНЕ них и точку возврата строят при ЖИВОМ базлайне, без всякого Ctrl+Z (замер `MEASUREMENTS §83ж`, §86):
· **правка полигона** — `_enter_polygon_editing_mode` не зовёт `set_mode`, а её ветка в `mousePressEvent` стоит РАНЬШЕ сторожа резайза, поэтому все четыре жеста с вершинами работают внутри «Размеров». Превью снимается на входе в правку (оверлей вершин строится из `segmentation`, то есть из превью) и в каждой из трёх точек снимка (`_undo_point()`) — превью можно поднять и ПОСЛЕ входа, панель никуда не девается;
· **ПКМ по приколотому концу трубы** — `contextMenuEvent` не проверяет ни режим, ни состояние, и `_unpin_endpoint` строит `AutoFixCommand`;
· **фиксация призрака вставки** — Ctrl+V поднимает призрак в базовом состоянии, кнопка «Размеры» его не гасит (гасит только перерисовка сцены), и Ctrl+ЛКМ фиксирует `_paste_node_clipboard`.
На **полигонах** цена этой половины другая: `_resize_node_poly` масштабирует ОТНОСИТЕЛЬНО базлайна, а `_resize_node_box` задаёт размер АБСОЛЮТНО, поэтому пересъём базлайна поверх живого превью возводил масштаб в квадрат — 605×75 → ×2 → 1210×150 → «Применить» тем же ×2 → 2420×300, и исходные 605×75 не возвращались НИКАКИМ числом Ctrl+Z (замер `MEASUREMENTS §83.27`). На боксах та же дорога самолечится, потому что арифметика абсолютная, — из-за этого дефект и дожил: в наборах превью полигонов не было ни одного.

⛔ **Тот же выход у OCR-слоя (пункт 1.x8, 2026-08-19).** Состояние (`display_regime`) и инструмент (`_current_mode`) — **независимые оси**: `set_display_regime` сбрасывает в idle только инструменты своего состояния, а `resize_objects` в этом списке нет, и кнопка «Размеры» лежит в ряду «всегда видимых». Значит «ОКР привязка» + «Размеры» включаются **одновременно**, панель ОКР остаётся на экране, выделение блоков переживает смену инструмента, и OCR-команда достижима поверх живого превью. Достижимы те пути, чей сторож — только `display_regime`: Delete по выделенным блокам, вставка блоков (Ctrl+V → Ctrl+ЛКМ; призрак обрабатывается в `mousePressEvent` до диспетчера режимов), правка текста блока и ручной KKS (Ctrl+2ЛКМ — проверки режима в `mouseDoubleClickEvent` нет вовсе) и **асинхронный приход результата распознавания** (`_on_recognize_done`: пока поток жив, гасятся «Распознать», «Сохранить» и «Подтвердить», а «Размеры» — нет). Пути, перехваченные режимом (Ctrl+ЛКМ, Ctrl+ПКМ, Shift, жесты `OcrBindHandler`), недостижимы. Лечение — одна строка в `OcrLayerMixin._ocr_push_snapshot`: это **единственная** точка построения точек возврата всего слоя, в отличие от `advanced_graph_editor` с его ~25 местами. Граница «команда, точки возврата не построившая, превью не снимает» держится по построению: все зовущие делают ранний выход «нечего делать» ДО этого вызова. Замер — `MEASUREMENTS §73`. ⛔ **Ручки размера текст-блока — резидентное состояние, и их точка возврата снимается на ПЕРВОМ КАДРЕ ПРОТЯЖКИ, а не при показе ручек** (пункт 1-40, §83.30): ручки переживают смену инструмента и живут сколько угодно долго (снимают их только выход из «ОКР привязки», Esc, удаление блока и клик по пустому месту), поэтому снимок, взятый при показе, вбирал в себя чужую ПОДТВЕРЖДЁННУЮ команду — и один Ctrl+Z по размеру блока откатывал ЕЁ. Замер `MEASUREMENTS §121`: удалённый блок возвращался на схему первым же Ctrl+Z после протяжки ручки. Между первым кадром протяжки и отпусканием такого окна нет — оператор держит кнопку мыши.

⛔ **Базлайн протухает от чужой команды.** Между его снятием и применением может пройти Ctrl+Z / Ctrl+Y — тогда базлайн описывает то, что оператор уже отменил, и откат по нему отменил бы сам откат. Сторож — `_resize_baseline_alive()`; протух — превью снимается там, где оно ещё наше (`_rollback_owned_preview`), и только потом базлайн снимается заново. Сравнивать `nodes`/`edges_data` по ссылке для этого **нельзя**: команды вроде `DragNodeCommand` правят узлы на месте и модель не пересобирают (замер `MEASUREMENTS §48`, сторож 1).

⛔ **У сторожа ДВА мнения, и первое — косвенное (вторая доработка 1.4, 2026-08-19).** `undo_mgr.revision` растёт на ЛЮБОЙ мутации стека, тогда как «модель пересобрали» верно только для undo/redo снимочных команд. `OptimizeEdgeCommand.undo` и `DragNodeCommand.undo` правят словари НА МЕСТЕ: один Ctrl+Z по такой команде объявлял базлайн мёртвым, хотя превью физически оставалось в модели, — и **все шесть потребителей `drop_uncommitted_preview()` вырождались в no-op одновременно** (четыре кнопки, воронка OCR, путь записи). Минимальная форма — три действия оператора и ни одной инъекции: перенос узла → «Размеры» + превью → Ctrl+Z → «Сохранить» клало на сервер `[-10.0, 188.0, 80.0, 278.0]` при исходных `[25, 215, 45, 251]`, стек 0, `can_undo` False, диалогов ноль (замер `MEASUREMENTS §83.6`). Худший случай — `apply_resize`: он снимал точку возврата ПОВЕРХ живого превью, и отмена до дна стека не возвращала исходные 20×36 вовсе. Поэтому у сторожа есть второе, **прямое** мнение — `_preview_still_in_model()`: у каждого узла набора сверяется отпечаток геометрии с тем, что вписал последний `_apply_sizes_from_base`. `model.restore` кладёт в словари состояние ДО превью — отпечатки расходятся, и ветка «бросить без отката» отрабатывает честно; правка на месте отпечатков набора не трогает — превью наше, и оно снимается.

⛔ **Прямое мнение отвечает ПОЭЛЕМЕНТНО, а не «всё или ничего» (третья доработка 1.4, 2026-08-20).** Агрегатный вердикт по набору верен ровно пока набор ОДНОРОДЕН. Чужой Ctrl+Z по переносу узла, который сам входит в набор, возвращает ему centroid/bbox/segmentation и честно стирает превью **только на нём** — а базлайн объявлялся мёртвым для ВСЕХ, и превью остальных вваривалось. Те же три действия оператора, что выше, только перенесённый узел — из набора (`armatura_ruchn`, 17 экземпляров): на сервер уезжал `node_11` = `[-10.0, 188.0, 80.0, 278.0]` при стеке 0, а на полигонах «Применить» ×2 после Ctrl+Z давало 2420×300 при недостижимых 605×75 (замеры `MEASUREMENTS §97.1`, §97.2). Лечение — `_preview_live_fields()`: он отвечает картой «узел → поля, где превью ещё лежит», а `_rollback_owned_preview()` снимает ровно их. Границу §48 это не ослабляет: поля, которые чужой откат вернул, в карте не значатся, и превью того узла не воскрешается. **Вторая ось — поля**: откат возвращает узлу не всё сразу (`DragNodeCommand.undo` не трогает `area`), поэтому отпечаток сверяется по полям, а не одним кортежем — иначе превью в непокрытом поле переживало откат навсегда (`area` 1428 → 8100 доезжала до сервера, замер `MEASUREMENTS §97.3`). **Третья ось — пины**, и она поэлементная по той же причине: см. следующий абзац.

⛔ **Чужой откат возвращает и ПИНЫ — граница «команды-на-месте их не трогают» ОПРОВЕРГНУТА исполнением (четвёртая доработка 1.4, 2026-08-20).** Прежняя редакция этого раздела утверждала обратное; перебор вёлся по двум командам из трёх. Полный перебор `ui/editors/commands/` (греп `^class .*Command`, 22 класса плюс два базовых; таблица «команда × что возвращает undo» — `MEASUREMENTS §106.3`) даёт **ровно одну** команду-на-месте, чей `undo` пишет пины: `ResizeNodeCommand` — штатный угловой ресайз бокса (в «Ручной правке» достижим двойным кликом по equipment-боксу → `_enter_resize_mode`), её `_apply_pins(old_pins)` возвращает пин вместе с рамкой и `area`. Безусловный `_restore_resize_pins()` в откате превью затирал возвращённый пин базлайном: пин `dx` 10.0 → угловой ресайз 20.0 → «Размеры» + превью 45.0 → Ctrl+Z (пин честно вернулся к 10.0) → «Сохранить» клало на сервер **20.0 при ОТКАТНОЙ рамке `[25, 215, 45, 251]`** — рассинхрон рамка/пин, персистентный в JSON (`pin_source`/`pin_target`; замер `MEASUREMENTS §106.4`, атрибуция §106.5: на коде до правки этого не было). Лечение — `_rollback_owned_resize_pins()`: у пинов свой отпечаток (`_resize_pin_preview` — что оставило в них превью), и след снимается ровно там, где он совпал. **Граница держится теперь ПРЯМЫМ ответом, а не перечнем команд — НА ПУТИ ОТКАТА ПРЕВЬЮ**: список выше — доказательство, а не условие (зонд ревизора командой, которой в перечне нет: пин уцелел на обеих полярностях, замеры `MEASUREMENTS §110.16` и §110.17). Обе полярности заперты зондами: снятый чужим откатом пин не воскрешается, а свой след снимается всегда — иначе конец трубы держится по рамке 90×90 при вернувшейся 20×36 (замер `MEASUREMENTS §48`). ⚠ Измерители тестов до этой доработки сверяли ТОЛЬКО узлы, поэтому порча пина проходила мимо всех пяти гейтов пункта: на дереве с живым дефектом узловой отпечаток всех 66 узлов совпадал бит-в-бит, расхождение было ровно одно и только в ребре (замер `§106.6`). ⚠ На пути ПЕРЕСЪЁМА базлайна то же обещание оказалось НЕВЕРНЫМ — следующий абзац.

⛔ **Пересъём базлайна судил только по узлам — и отменял чужой Ctrl+Z (пятая доработка 1.4, 2026-08-20).** Вердикт «базлайн жив» спрашивают ровно два места (греп `_resize_baseline_alive` по `advanced_graph_editor.py`): `preview_resize` и `apply_resize`; путь записи агрегата не спрашивает вовсе. Оба спрашивающих ведут в `_apply_sizes_from_base`, а он возвращает пины к базе БЕЗУСЛОВНО — идемпотентность бегунка. Пока сторож `_preview_still_in_model()` сверял только четыре УЗЛОВЫХ поля, откат, вернувший ОДНИ ПИНЫ, оставался ему невидим: базлайн считался живым, пересъёма не было, и в пин писалась протухшая база. Предпосылка «жив по узлам ⇒ пиновая база актуальна» держалась не сторожем, а перечнем команд — тем самым, от которого лечение только что отвязали. Замер `MEASUREMENTS §110.18`: команда-наследник ставит пин 33.0 → «Размеры» + превью (след 148.5) → Ctrl+Z (пин честно вернулся к 10.0) → второй тик бегунка снова даёт **148.5** вместо 45.0, «Сохранить» уносит на сервер **33.0 при стеке 0**, а через `apply_resize` протухший пин вмуровывается в точку возврата: отмена до дна стека даёт 33.0, и 10.0 недостижимо (замер §115). Лечение — тот же ПРЯМОЙ вопрос, что и в откате: отпечаток `_resize_pin_preview` у пинов уже был, сторож теперь его сверяет (`_snapshot_resize_pins() == _resize_pin_preview`), и пиновая половина перестала зависеть от перечня на ОБОИХ путях. ⚠ Что здесь замерено и что нет: ЛЕЧЕНИЕ проверено зондом на всех трёх потребителях (запись · пересъём в `preview_resize` · пересъём в `apply_resize`) — половина Д набора `tests/ui/test_preview_after_foreign_action.py`; ⛔ СЕГОДНЯШНИМИ командами дефект был НЕДОСТИЖИМ и порчи данных в дереве не было — единственная команда-на-месте, пишущая пины (`ResizeNodeCommand`), всегда пишет и bbox, то есть убивает базлайн узловой осью (замер §110.21). Опасность была в НАСЛЕДНИКЕ, поэтому команду-наследника заводит сам тест. ⚠ Быстрый выход сторожа (`revision` не двигался → базлайн жив) пиновый отпечаток НЕ сверяет: без мутации стека команды не было. Пин, изменённый мимо стека при неподвижном `revision`, остаётся НЕЗАКРЫТЫМ: пункт 1-40 перебрал девять смежных сценариев (`MEASUREMENTS §121`), и этой клетки среди них нет.

⛔ **Набор «Размеры» переживал перерисовку сцены НЕВИДИМЫМ (пункт 1-40, 2026-08-24).** Жёлтые рамки набора рисуются на `zValue 9`, а `_redraw_all` сносит со сцены всё `> 0` и обратно их не строил — при живом наборе. Перерисовку зовут ~30 мест: цвет рёбер в шторке «Оформление», откат снимочной команды, правка KKS, «Применить». Замер `MEASUREMENTS §121`: 17 рамок на сцене → **0** при `_resize_sel` = 17. Цена не косметическая: пока набор невидим, оператор не знает, что инструмент держит узлы, и не замечает ни одной из ловушек ниже. Лечение — `_redraw_all` перерисовывает рамки сам, `_reset_scene_state` снимает мёртвые ссылки на них (рядом с `waypoint_markers`, `_grid_items` и прочими списками сцены). ⚠ С блока 1 линии «Ручная правка + FXML» (2026-08-25) рамки строит не сам `_redraw_all`, а общий хвост `_redraw_overlays()` — абзац ниже.

⛔ **Слои холста гибли ЦЕЛИКОМ на переключении листа и подложки (блок 1 линии «Ручная правка + FXML», 2026-08-25).** Пересборку сцены зовут два переключателя шторки «Оформление» — «Светлый лист» и «Показать подложку» (`BaseGraphEditor.set_light_theme` / `set_background_visible` → `setup_scene`), а `setup_scene` делает `scene.clear()` и рисует заново только лист, подложку, рёбра и узлы: всё advanced-специфичное восстанавливал единственный `_redraw_all`, которого на этом пути не было. Замер `MEASUREMENTS §MEFX1`: скины 3 → **0**, сетка 27 → **0**, OCR-блоки 6 → **0**, жёлтые рамки «Размеров» 2 → **0**, подсветка выделенных узла и ребра 1/1 → **0**, всего предметов сцены 53 → **13**. Флаги при этом живы (`show_skins`, `grid_visible`, набор, выделение) — отсюда жалоба оператора «кнопка „Скины“ горит, а скинов нет»; лечится она была только выключить-включить. Лечение — одна точка восстановления вместо двух: `AdvancedGraphEditor.setup_scene` переопределён (`super()` + хвост), хвост вынесен в `_redraw_overlays()`, и его зовут ОБА пути. Порядок вставки значения не имеет — z у слоёв явные (сетка 0.5, скины 2.5, подсветка 6-7, рамки 9). ⛔ **Живые оверлеи снимаются ДО `clear()`**: `scene.removeItem` отдаёт предмет владельцу, а `clear()` его РАЗРУШАЕТ, поэтому правка полигона, ручки текст-блока и рамка добавления блока переживали переключение ссылками на мёртвые объекты C++ и роняли следующий жест оператора `RuntimeError` (все три воспроизведены, §MEFX1в). Через `_redraw_all` тот же жест не падает — там предметы живы, и сброса не требуется. ⚠ Зум и пан переключение по-прежнему сбрасывают (`fitInView` в `setup_scene`) — смежная боль, отдельное решение.

⛔ **Толщина трубы и разрывы мостов расходились с выгрузкой (блок 2 линии «Ручная правка + FXML», 2026-08-25).** Договор 1:1 (`base_graph_editor.py:102-110`) обещает «что оператор видит, то и уйдёт в FXML», и врал в трёх местах сразу. **(1)** Холстовый путь звал генератор с `use_diameter=True` (дефолт `canvas_to_fxml.generate_canvas_fxml`), и `calculate_diameter_stroke` превращала Dv300 в **12.0** при **2.0** на холсте — вшестеро. Решение Максима 2026-08-25 №1: у толщины ровно два источника — дефолт `LINE_STROKE_WIDTH` = 2.0 (== редакторский `EDGE_WIDTH`) либо кисть оператора `render_width`; диаметр ни при чём. Дефолт выключен; ветка `calculate_diameter_stroke` жива для легаси `generate_fxml` и ключа CLI `--no-diameter`. ⚠ Осознанная плата: одинаковая толщина меняет и МОСТЫ выгрузки — «кого рвать» решает теперь горизонтальность, а не диаметр, и разрыв становится однородным (замер `MEASUREMENTS §MEFX2б`: на `089feca2` те же 5 рёбер, но разрыв 6 px вместо 36). **(2)** `render_width` попадал в перо только в состоянии `style` или при включённых скинах — в `base` и «ОКР привязке» холст показывал 2.0 там, где в файл уходило 7.0. Теперь кисть видна везде, кроме `perp`: там ширина несёт собственный смысл — сигнал «ребро неперпендикулярно» (`EDGE_WIDTH + 1`); включённые скины старше состояния и показывают кисть и в нём. **(3)** Разрывы на пересечениях труб («— | —») считал только генератор, на холсте их не было вовсе. Решение №2: при включённых «Скинах» рёбра рисуются с разрывами по `graph_to_fxml.compute_bridge_cuts` — ТОЙ ЖЕ функцией и ТЕМИ ЖЕ аргументами, что уйдут в выгрузку (`base_stroke` = `EDGE_WIDTH`, `use_diameter=False`, `graph_scale=1.0`); режет полилинию тот же `_split_polyline_with_gaps` генератора, второй копии правила «где рвать» нет. ⛔ **Результат никуда не сохраняется**: разрывы остаются вычисляемыми, файл графа от предпросмотра не меняется. Ребро остаётся ОДНИМ `QGraphicsPathItem` — куски разделяет `moveTo`. ⚠ **Пересчёт зовётся из `_before_draw_all_edges`, а не из `_redraw_overlays`**: оверлеи рисуются ПОСЛЕ рёбер в обоих путях перерисовки, и посчитанные там разрывы приезжали бы на одну перерисовку позже. ⛔ **Разрывы обязан обновлять КАЖДЫЙ жест, а не только полная перерисовка (доработка по возврату приёмки, 2026-08-25).** Первая редакция считала их лишь в `_before_draw_all_edges`, то есть на пересборке сцены, — а жесты, которые обновляют пути рёбер поштучно (`_update_edge_path`), оставляли на холсте разрывы ПРОШЛОЙ перерисовки: новое пересечение без разрыва, снятое — с разрывом, висящим в воздухе. Жалоба оператора: «новые разрывы после перетаскивания коннектора — не всегда». Замер `MEASUREMENTS §MEFX2ж`: битых путей было пять — тяга конца ребра, тяга УЗЛА (`SnapshotCommand.finalize()` перерисовку НЕ зовёт, её видят только `undo`/`redo`), протяжка waypoint, `redo` гранулярной команды и удаление ребра-моста. Лечение — не список жестов, а единственная дверь мутаций модели: `UndoManager` получил хук `on_commit` (зовётся из `execute` / `push_executed` / `undo` / `redo` — там же, где растёт `revision` для дёрти-флага), редактор вешает на него `_sync_bridge_cuts`. ⛔ **Перерисовываются НЕ рёбра жеста**: разрывы считаются по всему листу, оператор тянет одну трубу, а рвётся соседняя, — адрес работы даёт сверка старых и новых разрывов ПО ЗНАЧЕНИЮ (разрыв умеет уезжать по длине ребра, оставаясь тем же ключом). ⚠ **Цена квадратична по рёбрам**, поэтому дверь остаётся на ЗАВЕРШЕНИИ жеста: кадры протяжки до `undo_mgr` не доходят, и во время жеста разрывы держатся прежними. Замер `§MEFX2ж`: жест платит 2.0 / 3.3 / 6.7 мс на 63 / 74 / 118 рёбрах и 139 мс на синтетике 402/418; полная перерисовка рёбер на том же месте стоила бы 8.8 / 10.5 / 22.6 / 169 мс — дороже везде, поэтому взят дешёвый путь. Пачка команд одной кнопки («Оптимизировать все» — команда на каждое ребро) дверь глушит и сводит картину один раз в `finally`: без глушителя 55 рёбер стоили бы 466 мс вместо 44. ✅ **Множитель разрыва доведён до предпросмотра (7.5, mefx-7).** `bridge_gap_factor` живёт per-uid в `UISettings` и до правки попадал только в запрос генерации (`advanced_graph_tab.py` → `diagram_workspace.py:2370`), а редактор про `uid` не знает — предпросмотр шёл на дефолте 3.0, и оператор, сдвинувший бегунок, видел новую ширину только в готовом файле. Теперь вкладка кладёт его в `editor.bridge_gap_factor` на ДВУХ путях: по кнопке «Применить разрыв» (`_on_bridge_gap_changed` — настройка плюс `_sync_bridge_cuts`, та же дверь пересчёта, что у жестов) и при открытии вкладки из сохранённой настройки (`apply_saved_appearance`) — панель «Размеры» создаётся лениво и может не открываться вовсе, а генерация читает настройку всегда. Экран и файл сходятся при ЛЮБОМ положении бегунка; заперто в `tests/ui/test_canvas_fxml_parity.py` двумя случаями (жест оператора и переоткрытие вкладки).

⛔ **Подписи на холсте были не того размера, что в файле, а подпись диаметра висела во всех состояниях (блок 3 линии «Ручная правка + FXML», 2026-08-25).** Кегль подписи, УХОДЯЩЕЙ В ФАЙЛ, теперь ОДИН и фиксированный — **18** (решение Максима 2026-08-25 №3), таблица `modules/graph_to_fxml.TEXT_STYLES`, и её же читает редактор у подписи текст-блока ОКР-слоя (`ocr_layer_mixin._LABEL_PX`). Было четыре числа в файле (40.0 у `<Text>`, 10.0 у холстового KKS, доли `0.35·min(w,h)` и `0.4·min(w,h)` у растрового). ⛔ **Подпись диаметра файловой константе НЕ подчиняется** (решение Максима по доработке mefx-3): в FXML её нет вовсе, паритета с файлом у неё нет, поэтому кегль у неё свой, внутренний и прежний (`QFont("sans-serif", 6)`, `base_graph_editor._create_edge_label`) — одинаковый во всех вкладках, включая «Проверку схемы». ⛔ **На экране кегль подписи текст-блока задаётся ПИКСЕЛЯМИ и без `_ocr_vis_scale()`**: кегль FXML — это em в координатах ХОЛСТА, ровно тех, в которых живёт сцена; домножение на вписывание растра давало на боевом листе (`_bg_scale` ≈ 0.22) подпись ~2 px против 40 в файле, а `pointSize` дал бы на 96 dpi 24 px вместо 18. ⚠ **Общий у экрана и выгрузки только кегль подписи текст-блока**: Tahoma фиксируется ТОЛЬКО в FXML, в клиент шрифт не бандлим (решение №7), семейство на экране прежнее — `DejaVu Sans` у подписи блока, `sans-serif` у диаметра. ⛔ **Подпись диаметра теперь живёт по правилу ОКР-слоя** — видна только в состоянии «ОКР привязка», в остальных скрыта (решение Максима по приёмке mefx-2). Это паритет 1:1: в FXML подписи диаметра нет вовсе, а правит её единственный жест — Ctrl+2ЛКМ по ребру в том же состоянии. Механизм не свой: виртуальный `_edge_label_visible()` в Base (по умолчанию «видна») переопределён в `OcrLayerMixin`, то есть решает тот же слой, что показывает и прячет текст-блоки. Подпись при этом НЕ удаляется, а скрывается — `_update_edge_path` и `remove_edge_item` работают по `edge_label_items`. Видимость переживает переключение «Светлого листа» и «Показать подложку»: подпись строится вместе с ребром, а рёбра пересобирает `setup_scene` (хвост блока 1). Замер `MEASUREMENTS §MEFX3`: рендером в JavaFX 18 (движок SceneBuilder) промах центра подписи по X упал с 33.85 px до 1.58 px, площадь подписи против площади рамки — с 5.4× до 1.5×; при этом 33 подписи листа из 48 по-прежнему выше своей рамки — это осознанный размен кегля 18, показанный Максиму глазами.

⛔ **Точка возврата «Применить» — про ВСЮ модель, а сторож судил по набору (пункт 1-40, §103.18).** `apply_resize` кладёт в `cmd._before` снимок `_resize_model_base`, то есть состояние ВСЕЙ схемы до превью, — а `_resize_baseline_alive()` отвечает на другой вопрос: годится ли `_resize_base` для идемпотентного пересчёта РАЗМЕРОВ НАБОРА. Между этими вопросами и жил дефект: команда, легшая в стек после съёмки базлайна (или снятая с него Ctrl+Z), отпечаткам набора невидима. Замеры `MEASUREMENTS §121`: перенос узла ВНЕ набора, отменённый оператором, ВОСКРЕСАЛ отменой до дна при стеке 0 и `can_undo` False — вернуть нечем; узел, воскрешённый Ctrl+Z между превью и «Применить», откат «Применить» удалял снова. Лечение — точка возврата пересобирается всегда, когда `revision` двигался: своё превью снимается поэлементно, снимок берётся с модели как она есть.

⛔ **`area` и пины — ПРОИЗВОДНЫЕ от рамки, и возвращать их из базлайна можно не всегда (пункт 1-40, §110.25).** Совпадение поля с отпечатком превью ПО ЗНАЧЕНИЮ владения не доказывает: у бокса `segmentation` пуст с обеих сторон, а redo углового ресайза ТОЙ ЖЕ ширины считает и рамку, и пин одной формулой от одной базы (10.0 × 90/20 = 45.0 с обеих сторон) — отпечаток совпадает СТРУКТУРНО, и это воспроизводимый жест оператора (Ctrl+Y), а не лотерея битов. Откат превью писал в такой узел базу поверх чужой рамки: серверу уезжали рамка redo, `area` 720 при 90×90 и пин исходной формы — рассинхрон, персистентный в JSON. Лечение — `_base_describes_frame()`: производные возвращаются, только пока база описывает нынешнюю рамку (её сейчас же вернём сами либо она уже базлайнового РАЗМЕРА — чужой откат переноса размера не менял, и `area` вернуть надо, замер §97.3). Граница заперта с двух сторон: сторож, всегда говорящий «да», краснит сценарий redo; всегда говорящий «нет» — 28 тестов семьи превью.

⛔ **Превью полигонов было неидемпотентно ПО ПИНАМ (пункт 1-40, §110.26).** `_apply_sizes_from_base` возвращает боксу базовый `bbox` и потому отдаёт `rescale_edge_pins` пару «база → цель»; у полигонов `bbox` не возвращался, и пара становилась «прошлый тик → цель». От базы 10.0 бегунок давал ×2 → 20.0, ×3 → **15.0** вместо 30.0, возврат к ×2 → **6.67**; «Применить» тем же ×2 давало множитель 1.0 и уносило на сервер пин ИСХОДНОЙ формы при удвоенном контуре — конец трубы оказывался внутри контура, а не на границе. Геометрия при этом верна на каждом тике, поэтому глазом не видно вовсе, а измерители пинов на полигонах не стояли ни в одном наборе. Лечение — одна строка: та же, что в боксовой ветке.

⛔ **Тик автосохранения ВОСКРЕШАЛ превью, снятое оператором — судьба СМЕШАННОГО состояния заявлена (доработка 1-40 по возврату ревизии связки, 2026-08-24, `MEASUREMENTS §124`).** Набор к моменту фонового тика бывает смешанным: чужой Ctrl+Z по переносу узла, который сам входит в набор, возвращает ЕМУ геометрию и честно снимает превью **только с него**, у остальных превью живо; а откат снимочной команды (`model.restore`) стирает превью **целиком**. Первая редакция возврата пересчитывала превью заново (`preview_resize` тем же жетоном), то есть вписывала его во ВЕСЬ набор, — и обе половины ломались по-разному. Замеры: `node_11` уезжал с откатных `[25, 215, 45, 251]` обратно на `[-10, 188, 80, 278]` без единого действия оператора (§124.3); на пиновой грани тик перекрывал возвращённые откатом рамку и пин — 60×60 и пин 30.0 при откатных 20×36 и 10.0 (§124.4); после полного стирания превью возрождалось во весь набор через ≤120 с (§124.5). ⭐ **Корень — детектор жетона, и это та же ловушка «совпадение ПО ЗНАЧЕНИЮ ≠ владение», что абзацем выше:** «есть ли живое превью» спрашивалось у `_preview_live_fields()`, а тот отвечает на другой вопрос — «что откатывать», где совпадение неизменённого поля безвредно (возврат базы в него no-op). У бокса превью не двигает `centroid`, а `segmentation` пуст с обеих сторон, поэтому после ПОЛНОГО сноса детектор насчитывал **17 узлов из 17 живыми** по этим двум полям (§124.6). Лечение — две части. **(1)** `_preview_owned_fields()`: живым считается поле, которое ещё в модели И которое превью РЕАЛЬНО изменило (отпечаток разошёлся с базлайном). **(2)** Тик возвращает СНИМОК холста (`_snapshot_preview_canvas` / `_restore_preview_canvas`), а не рецепт его пересчёта: между снятием и возвратом модель не мутирует — запись читает её и синхронизирует только метаданные `graph` (`GraphDataModel.save`), — поэтому дословный возврат снимка и есть обещанная «ровно та же картинка». ⚠ **Граница названа явно:** тик возвращает то, что снял, и ничего сверх — отменённое оператором остаётся отменённым, живое превью остаётся живым, обе половины набора переживают запись каждая в своём состоянии. Обратный выбор («тик пересобирает превью на ВЕСЬ набор, как жест бегунка») отвергнут: фоновому тику пришлось бы отменять часть Ctrl+Z оператора — ровно то, ради чего этот сценарий и заводился. ⛔ **Данные при этом не портились ни разу:** во всех сценариях ревизии сервер получал зафиксированное (гейты 1.4 отработали) — дефект был холста, и цена его в том, что оператор видит не то, что сделал.

**Пин входа (модель «пин на ребре», 2026-08-03).** Единственное персистентное намерение оператора — пин входа: `edge['pin_source'|'pin_target']` = `{'dx','dy'}`, локальное смещение **(x, y)** от центроида узла конца (едет с узлом, масштабируется при resize через `rescale_edge_pins`, переживает undo/save). API — `modules/graph/core/ports.py`, секция «пины на ребре» (`pin_role` / `edge_pin` / `pinned_on_node` / `set_edge_pin` / `clear_edge_pin` / `rescale_edge_pins`); `ui/editors/port_model.py` — тонкий реэкспорт. Посадка (`seat_end`, `modules/graph/core/edit_engine.py`) сажает конец в пин первее всего; пин на коннекторе запрещён — конец коннектора всегда центроид. Жесты (режим edit_waypoint): протяжка маркера конца ставит/двигает пин (конец липнет к портам); «отвязать вход» — ПКМ по маркеру конца; маркеры портов на время протяжки: голубые — кандидаты (производные, не хранятся), оранжевые — пины. Waypoints — кэш последнего расчёта маршрута: drag узла ведёт все инцидентные рёбра, любой жест вправе перестроить маршрут. Флаги `_manual_route`/`_auto_route` и якоря `node['_ports']` мертвы (до 2026-08-03, мигрируются при открытии — см. §5.5). Пины не входят в sha-проекцию холста (`graph_projection_sha`) и не текут в FXML.

**Auto-fix** (`autofix_chains.py`): выравнивает узлы по ортогональным цепочкам. Union-Find для H- и V-цепочек, weighted median, clamp для equipment/connector, multi-pass до сходимости.

**Edge routing** (`edge_routing.py`): ортогональный маршрутизатор. Правила: ортогональность, перпендикулярный выход, stub ≥5px, не через bbox, уникальность, минимум поворотов. Pipeline: distribute connection points → generate candidates (L/Z/U) → filter bbox → score → clean collinear.

**Perp stats:** статистика перпендикулярности рёбер (`global_axis_perpendicularity`). Показывает: % perfect (0° deviation), % acceptable (<5°), worst cases.

## 7. Mask Editors

### 7.1 PolylineMaskEditor

Файл: `ui/editors/polyline_mask_editor.py`.

`QGraphicsView` для валидации маски труб. Два инструмента:

**Полилиния (рисование):** Ctrl+ЛКМ добавляет точки, 2×ЛКМ / ПКМ / Enter завершает. Рисует на маске белым (`cv2.polylines` + `cv2.fillPoly`).

**Ластик (стирание):** Ctrl+ЛКМ + drag стирает чёрным кругом (размер из slider).

Undo: стек масок (numpy arrays), до `MAX_UNDO_STEPS=50`.

Оптимизации: numpy vectorized mask↔RGBA конверсии, Grayscale 8-bit подложка (28 MB vs 112 MB на 7000×4000), COCO bbox через QPainter.

Ctrl+S в редакторе делегируется вкладке (`save_requested_callback`, пункт 1.19 — как в §7.2). Напрямую `save_mask()` без пути звать нельзя: по умолчанию он пишет в ОТНОСИТЕЛЬНЫЙ `pipe_mask_validated.png`, то есть PNG падает в CWD процесса и на сервер не уходит, а оператор при этом читает в статусе «Сохранено».

### 7.2 SquareMaskEditor

Файл: `ui/editors/square_mask_editor.py`.

`QGraphicsView` для валидации junction/bridge масок. Два класса масок:

- **Junction** (белая маска, клавиша `1`).
- **Bridge** (красная маска, клавиша `2`).

Инструменты: Ctrl+ЛКМ добавляет квадрат (размер из slider, default 15px). Ctrl+ПКМ — flood-fill удаление (BFS по связным компонентам маски). Shift+протяжка — обвести и выделить пятна (золотая рамка), Esc — снять выделение.

**Изменение реального размера** — `apply_square_size(size)`: пятно стирается **по связной компоненте** (не по bbox: у L-образных клякс bbox'ы соседей перекрываются, и стирание по bbox съело бы чужие пиксели), затем квадраты `size×size` рисуются заново **по центрам**. Только это разъединяет слипшиеся при сжатии и сохраняет квадратность; число связных компонент при этом легально меняется. Центры — независимый список (`_points`), он и есть источник истины; правило выбора: точка модели выигрывает только для merged-компонент, для одиночного квадрата надёжнее центроид пятна (оператор мог его передвинуть).

Свежепоставленные квадраты живут отдельными `QGraphicsRectItem` и в Shift-выделение не попадают никогда — ветка «все пятна класса» меняет и их.

Undo: стек снимков. Запись операции размера хранит обе маски, геометрию свежепоставленных `QGraphicsRectItem` и список центров — снимка масок недостаточно.

Ctrl+S в редакторе делегируется вкладке (`save_requested_callback`). Напрямую `save_masks()` без путей звать нельзя — PNG упадут в CWD процесса и на сервер не уйдут.

### 7.3 FrameRemoverView («Очистка рамки»)

Файл: `ui/editors/frame_editor.py`, вкладка — `ui/tabs/frame_tab.py`.

Три инструмента: **Полигон** (всё снаружи → фон), **Бокс** (всё внутри → фон), **Обрезать** (лист уменьшается, DPI сохраняется, без ресэмпла).

**Предпросмотр обрезки.** Протяжка ЛКМ не режет лист сразу, а **паркует** зелёную рамку. До применения её можно поправить:

| Жест | Действие | Курсор |
|------|----------|--------|
| Тяга за любую точку стороны | двигать эту сторону | SizeHor / SizeVer |
| Тяга за угол | двигать обе стороны | SizeFDiag / SizeBDiag |
| Тяга внутри рамки | перенести целиком (кламп по листу) | SizeAll |
| Enter | применить обрезку | — |
| Esc | отмена | — |
| Клик мимо рамки | новая протяжка (старая рамка заменяется) | Cross |

Объектов-ручек нет — hit-test идёт по самому прямоугольнику, зоны ±6 экранных px при любом зуме. Вырожденная рамка (<5 px по стороне) отсекается сразу при завершении протяжки, а не молча по Enter.

**Ctrl+Z при живом превью** гасит превью, а не правку изображения: undo пересобирает сцену и убил бы превью-item посреди жеста. Следующий Ctrl+Z отменяет правку как обычно. Смена инструмента снимает припаркованное превью — это считается отказом от обрезки.

**Вопрос о несохранённом** (пункт 1.21). `FrameTab` была ЕДИНСТВЕННОЙ вкладкой без `has_unsaved_changes()` — из девяти классов контракт имели восемь, — а обе двери вопроса начинаются с `hasattr`. Поэтому «← Назад» и ✕ окна уносили обведённый полигон и убранный штамп молча, без единого диалога. Теперь контракт есть: «грязная» — когда длина стека отмены редактора отличается от той, что была на последней записи (`_saved_undo_len`), то есть и после «Отменить» тоже. Ответ «Да» идёт в `_save_image()` — общее тело для 💾 и для вопроса; «Подтвердить» = `_save_image()` + `complete_frame_removal`, поэтому подтверждённая вкладка чистая и второго вопроса не поднимает. ⚠ Известный предел: стек — `deque(maxlen=30)`, поэтому 31-я операция подряд длину не меняет; для этой вкладки (полигон + пара боксов + обрезка) недостижимо, лечится счётчиком мутаций в редакторе.

**Открытие вкладки и отказ загрузки** (пункт 1.x6). `FrameTab` строится и показывается сразу, а `original_image` качается ОТЛОЖЕННЫМ вызовом (`QTimer.singleShot(0, self, self._load_original)`) — то есть после того, как воркспейс вставил вкладку в layout и подключил её сигналы (`diagram_workspace.py:1752-1759`). Отказ загрузки (нет артефакта, сеть, битый файл) виден **строкой** под тулбаром и в статусбаре и уходит в файл лога клиента с трассировкой (§11.5). Модалки на этом пути нет намеренно: `QMessageBox` из конструктора вешал процесс под offscreen насмерть, а на бою всплывал над ещё не открытой вкладкой; `status_message`, отправленный из конструктора, не слышал никто.

## 8. OCR Binding Editor

Файл: `ui/editors/ocr_binding_editor.py`.

`QGraphicsView` для визуальной привязки OCR-блоков к узлам/рёбрам графа.

### 8.1 Визуальные элементы

- **OCR-боксы:** прямоугольники с текстом. Цвет по confidence: зелёный (≥0.94), жёлтый (0.80–0.94), оранжевый (<0.80). Привязанные боксы получают синюю обводку.
- **Equipment nodes:** синие маркеры. Hover — жёлтый, bound — оранжевый.
- **Рёбра графа:** бирюзовые polylines.
- **Secondary blocks:** кириллические описания (серые боксы).
- **Binding lines:** линии от OCR-бокса к привязанному узлу/ребру.

### 8.2 Взаимодействие

Единый UX через Ctrl + drag:

| Действие | Что происходит |
|----------|----------------|
| Ctrl+drag OCR-бокса → на equipment node | Привязка ККС к узлу |
| Ctrl+drag OCR-бокса → на ребро | Привязка диаметра к ребру |
| Ctrl+drag OCR-бокса → на другой OCR-бокс | Слияние боксов |
| Ctrl+drag OCR-бокса → на пустое место | Отмена (бокс возвращается) |
| Ctrl+click на привязанном боксе | Отвязка |
| Ctrl+double click | Редактирование текста |

### 8.3 Validation mode

В режиме валидации OCR-боксы раскрашиваются по результатам classify из domain profile. Цвета определяются для каждой категории (KKS, diameter, noise, other). Оператор может переклассифицировать блок, подтвердить или отклонить.

### 8.4 Diameter bindings

Привязка диаметров к рёбрам с propagation: если ребро получило диаметр, соседние рёбра без диаметра наследуют его по правилу потока. Labels диаметров показываются на середине ребра.

⛔ **Ручная правка диаметра — ШАГ отмены, а не запись мимо стека (пункт 1-40, §83.31).** Ctrl+2ЛКМ по ребру в состоянии «ОКР привязка» открывает диалог диаметра (`AdvancedGraphEditor._open_diameter_edit_dialog`), и он писал в `edge_data` НАПРЯМУЮ: `undo_mgr.revision` не рос, `has_unsaved_changes()` правку не видел (вкладка закрывалась без вопроса, автосохранение по ней не срабатывало), а первый же Ctrl+Z по соседней снимочной команде стирал её без следа — `_before` соседа снят ДО правки. Соседний путь ТОГО ЖЕ жеста, ручной KKS, точку возврата строил всегда — асимметрия, а не замысел. Теперь диалог берёт `_ocr_push_snapshot("Диаметр ребра")` и закрывает шаг после распространения по трубам: и сам диаметр, и propagation — один Ctrl+Z оператора. Пустой ввод, равный текущему значению, шага не создаёт.

**Сохранение по таймеру вопросов не задаёт** (пункт 1-38 дороги; было наоборот — долг, замеченный 1.33 и заперенный тестами 1.21). Сервис отнимает у вкладки право спрашивать на время тика (`with tab.non_interactive_save()`), а отказывается и объясняется сама вкладка: `NonInteractiveSaveMixin` (`ui/tabs/save_mode.py`) несут все четыре базовых класса карты — `BaseGraphTab`, `JunctionTab`, `PipeTab`, `OcrBindingTab`. Лечить это в сервисе было нечем: диалоги сидят у самих методов сохранения, и их восемь — `BaseGraphTab._confirm_blind_overwrite`, `BaseGraphTab._save_graph`, `ContourTab._save_graph`, `JunctionTab._save_masks`, `JunctionTab._upload_points`, `PipeTab._save_mask`, `OcrBindingTab._confirm_blind_overwrite`, `OcrBindingTab._save_binding`.

⛔ Запрет слепой перезаписи (§5.1, пункты 1.23/1-33/1-39) режим **не обходит**: молчаливый отказ по таймеру оставляет запрет взведённым, и ближайший ручной заход спросит снова. Иначе «Да» в фоновом диалоге снимало бы защиту насовсем — цена, ради которой пункт и заводился. Заперто набором `tests/ui/test_autosave_non_interactive.py` (перебор всей карты `_SAVE_METHODS` и всех восьми дверей, с обратной границей «у оператора модалка осталась»).

**Дёрти-флаг графовых вкладок** — верх undo-стека разошёлся с точкой сохранения (`BaseGraphTab.has_unsaved_changes`). ⛔ **Не счётчик мутаций** (блок 5, п. 5.2, 2026-08-25): `undo_mgr.revision` растёт на КАЖДОЙ мутации, включая undo и redo (`_committed` зовётся из всех четырёх дверей), поэтому полный Ctrl+Z возвращал дерево ровно к загруженному, а вкладка продолжала спрашивать о несохранённом и на выходе, и тиком автосейва. Замер: протяжка `node_11` → Ctrl+Z даёт `revision` 2 при отметке 0, стек пуст, рамка снова `[25, 215, 45, 251]` — и флаг грязный. Точка сохранения помечается САМИМ объектом `undo_stack[-1]` (`_mark_saved`) и сверяется по `is`: отмена ДО неё чистеет, отмена ЗА неё — нет, переполнение `deque(maxlen=100)` маркеру не страшно (позиция в стеке им застывает — коммент `undo_manager.py:109-111`). Взведённый РУКАМИ флаг (`ContourTab` при непрошедшей второй половине записи, п. 1-41) остаётся сильнее маркера: расхождение `_saved_revision` с отметкой читается как «грязно». Следствие для автосейва: вкладку, вернувшуюся к точке сохранения, тик больше не пишет — сохранять нечего. Считает только мутации, прошедшие через стек команд; живое превью панели «Размеры» идёт мимо стека, и флаг его **не видит намеренно**: превью без «Применить» оператор ещё не подтвердил, а грязный от превью флаг поручил бы автосейву отправлять именно его. Согласованность держится с другой стороны — `_save_graph` снимает незафиксированное превью перед записью (см. §6.3 «Живое превью не уходит на сервер»), поэтому **на сервер уходит ровно то, что считает флаг**. ⛔ **Но по таймеру превью снимается только НА ВРЕМЯ записи** (пункт 1-40, §83.32): тик — не жест оператора (то же основание, что у 1-38), а путь записи у него общий с кнопкой 💾, и раз в 120 с фоновый тик стирал размер, который оператор в эту минуту подбирал бегунком, — без единого его действия и без следа в стеке. `_save_graph` по таймеру зовёт `take_uncommitted_preview()` и возвращает превью в `finally` (`restore_uncommitted_preview`); по жесту — прежний `drop_uncommitted_preview()`, снимающий его насовсем. Инвариант 1.5 не ослаблен: серверу в обоих случаях достаётся ровно зафиксированное состояние. Возврат узкий — жетон пуст, если живого превью не было, поэтому подтверждённые размеры тик вторым разом не накатывает (на полигонах это был бы масштаб в квадрате). ⛔ **Что значит «жетон пуст» и что именно возвращается — перемерено ревизией связки (2026-08-24, `MEASUREMENTS §124`, доработка 1-40).** Первая редакция спрашивала «живо ли превью» у `_preview_live_fields()`, а тот считает живым поле, СОВПАВШЕЕ с отпечатком, — у бокса `centroid` превью не двигает, `segmentation` пуст с обеих сторон, поэтому «живо» собиралось даже когда превью стёрто ЦЕЛИКОМ (§124.6: 17 узлов из 17). Теперь спрашивается `_preview_owned_fields()` — поле обязано ещё и РАЗОЙТИСЬ с базлайном, то есть быть тем, что превью реально изменило. И возвращается тик СНИМКОМ холста, а не пересчётом `preview_resize`: к моменту тика набор бывает СМЕШАННЫМ, и пересчёт вписывал превью во ВЕСЬ набор — узел, с которого чужой Ctrl+Z превью снял, уезжал обратно (§124.3), а на пиновой грани тик перекрывал возвращённые откатом рамку и пин (§124.4). Замер `MEASUREMENTS §50` до правки: тик автосейва после протяжки увозил `node_11` = `[455.0, 355.0, 545.0, 445.0]` (протяжка + превью), тогда как в модели после выхода из режима оставалось `[490.0, 382.0, 510.0, 418.0]`.

Настройки из `UISettings`: `autosave_enabled` (default true), `autosave_interval_sec` (default 120).

**Оформление — по диаграмме.** Ключи вида `appearance/{uid}/{key}` (`get/set/has/clear_appearance`), плоские: один ключ действует на все вкладки диаграммы сразу, а общий сброс (`clear_appearance(uid)`) стирает всё поддерево. Побочный эффект принят как норма: сброс из любой вкладки сбрасывает и остальные, уже открытые вкладки увидят это после переоткрытия.

| Ключ оформления | Тип | Default | Где |
|-----------------|-----|---------|-----|
| `bg_darkness` | float % | 60 | все вкладки с шестерёнкой |
| `edge_color`, `edge_bad_color` | hex | — | графовые вкладки |
| `size_connector` | float % | 100 | Проверка схемы, Контуры, Ручная правка |
| `size_outline` | float % | 100 | то же (подпись — «Толщина контуров и маркеров») |
| `size_ocr_border` | float % | 100 | Ручная правка, Привязка подписей |
| `size_node` | float % | 100 | Привязка подписей |
| `side_marks` | bool | true | графовые вкладки (подсветка сторон) |
| `side_mark_color` | hex | цвет узла | то же |
| `bridge_gap_factor` | float | 3.0 | Ручная правка — ⚠ **единственный ключ таблицы, который уходит в ВЫГРУЗКУ**, а не только в картинку (§6.3) |

⛔ **Аудит регуляторов «Оформления» (7.3, mefx-7, 2026-08-25) — таблица и три ведра в `MEASUREMENTS §MEFX7.5`.** Перечень контролов снят С КОДА (перехват `AppearancePanel.add_*`): в шестерёнке «Ручной правки» их **десять**, и это не то же самое, что таблица ключей выше — `bridge_gap_factor` живёт в панели «Размеры», а `size_node` — в «Привязке подписей». Мерилось число предметов сцены, чей отпечаток меняется от крайнего положения регулятора, в четырёх состояниях; пол шума назван первым (0 везде, 14 при скинах — пиксмапы скинов пересоздаются). Итог, принятый решением Максима: **(1) «Ребро без диаметра» УБРАНО целиком** — 0 изменений во всех четырёх состояниях при поле шума 0; регулятор писал `COLOR_NO_DIAMETER`, у которой по всему репо не было **ни одного чтения** с тех пор, как из состояния «ОКР привязка» убрали красную подсветку рёбер без диаметра (заодно врала докстрока `_get_edge_color`, обещавшая «ocr → красный»); сняты контрол, ключ `edge_no_diam_color`, `set_edge_no_diameter_color` и сама константа. **(2) «Толщина рамки боксов» → «Толщина контуров и маркеров»** — имя было у́же действия: под пером ходят рамки bbox, контуры полигонов, маркеры коннекторов, OCR-маркеры и стрелки (424 изменённых отпечатка при 416 предметах сцены). ⚠ Жалоба «крутишь и не видишь» — не про регулятор: при включённых скинах рамка РИСУЕТСЯ, но скин (z=2.5) кроет её (z=2). Обводка выделения регулятору не подчинена — у неё своя `SELECTION_RING_WIDTH`. **(3) «Неперпенд. ребро» → «Неперпенд. ребро (в «Перпендикулярности»)»** — работает только в этом состоянии (64 предмета против 0 в трёх других). Остальные семь регуляторов честны и не тронуты; **ключи хранения при переименовании не менялись**, поэтому сохранённые настройки схем не протухли. Заперто в `tests/ui/test_size_regulators.py` (состав шестерёнки поимённо, снос мёртвого, сохранность ключей).

Размерные регуляторы — **только визуал**: в граф и FXML ничего не уходит. Хранится множитель в процентах от базы, а не абсолютный размер: редактор применяет его от собственной базы внутри `_apply_visuals`, поэтому значение переживает переключение системы координат (растр/холст) и не накапливается. Под множитель попадают только адресные ключи (`SIZE_FACTOR_KEYS`); геометрия (`CONNECTOR_MARKER_RADIUS`), hit-test (`CLICK_THRESHOLD`) и толщина трубы (`EDGE_WIDTH`, обязана совпадать с `graph_to_fxml.LINE_STROKE_WIDTH`) в него не входят.

### 11.5 Логи клиента

Файл: `ui/services/client_logging.py`. Ставится в `main()` (`ui/main.py`) первым делом, до создания `QApplication`.

| Функция | Что делает |
|---------|-----------|
| `setup_client_logging()` | консоль (как раньше) + `RotatingFileHandler`; возвращает путь файла или `None`, если каталог недоступен |
| `install_excepthook()` | необработанное исключение → запись `CRITICAL` с трассировкой, затем прежний `sys.excepthook` |
| `bind_uid(uid)` | uid открытой диаграммы в корреляционный контекст (зовётся из `DiagramWorkspace.load_diagram`) |

Конец сеанса виден так же, как начало: `MainWindow.closeEvent` (§2) пишет `Клиент закрывается` — до него лог обрывался на полуслове и «клиент закрыли» было не отличить от «клиент упал».

Отказ инструмента редактора виден там же (пункт ДН3): `AdvancedGraphTab._auto_fix` (§5.5) пишет строку с трассировкой и `uid`. До ДН3 она уходила в `sys.stderr`, которого в собранном `.exe` нет, и терялась целиком — прирост файла на отказе был 0 байт. Ловушка общая для клиента: `traceback.print_exc()` в `.exe` молчит не потому, что «мёртв stderr», а потому, что мертвы ОБА потока — при живом `stdout` печать уходит в него (замер `MEASUREMENTS §96`).

**Где лежит лог:** `%LOCALAPPDATA%\PID-Client\logs\client.log` (Windows), `~/.local/state/pid-client/logs/client.log` (Linux). Переопределяется переменной `PID_LOG_DIR`, уровень — `PID_LOG_LEVEL` (default `INFO`). Ротация: 5 МБ × 5 файлов.

Формат и корреляционные поля — общие с сервером (`app/core/logging.py`: `LOG_FORMAT`, `ContextFilter`), поэтому строка клиента читается так же, как серверная, и сшивается с ней по `uid=`. Контекст живёт в `contextvars`: в фоновых потоках вкладок (QThread) он свой, там `uid=-`.

Почему файл, а не stdout: в собранном `.exe` `console=False` (`deploy_ready/pid_client_windows.spec:82`) — у процесса нет ни `stdout`, ни `stderr`, и весь вывод пропадал. Файл открывается с `encoding="utf-8", errors="replace"`: эмодзи в сообщениях (💾 ✅ 🔄) иначе роняют запись на cp1251-машине.

### 11.6 ProgressModel — канон пайплайна

Файл: `ui/services/progress_model.py`. Чистый Python (без Qt): процент и ETA считаются на клиенте из строк `/stages`, без единого лишнего запроса к серверу.

Канон `_PIPELINE` — 13 стадий в порядке конвейера; веса берутся из `_DEFAULT_BUDGETS` (провизорные сиды, которые с шестого наблюдения перекрывает p50 сервера — `GET /api/stats/stage-durations`), подписи — из `_STAGE_LABELS`. Три карты обязаны иметь ОДНО множество ключей, и оно обязано совпадать с тем, что конвейер реально заводит: решётка `tests/observability/test_progress_model.py` снимает множество `StageType` разбором `app/**` и `worker/**` при каждом прогоне.

Блок болей 2026-08-25 (Б19) выправил канон: убраны три стадии-призрака (`upload`, `mask_validation`, `graph_validation` — строк с такими типами не заводит никто, а вес в знаменателе они держали, и процент структурно не доходил до 100: 92 % на пройденном конвейере против 97 % после правки), добавлена реальная `direction_classification` (свою строку она пишет с 2026-08-18, а в каноне её не было), и пара «финальная скелетизация / перекрёстки» поставлена в порядок исполнения — перекрёстки диспетчит сама финальная скелетизация, обратный порядок врал ETA.
