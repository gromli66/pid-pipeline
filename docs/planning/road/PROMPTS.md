# Готовые промпты — дорога 2026-08-17

## Шпаргалка Максима — весь цикл по шагам

**На каждый пункт:**
1. Новый чат → промпт исполнителя (ниже), `<ID>` = следующий не-done пункт волны из `BOARD.md`.
2. Ждать отчёт 5 строк. Отвечать только на STOP-вопросы.
3. Чек 30 сек: отчёт есть · тег `road-<ID>` есть · доска обновлена · красных флагов нет.
   Что-то не так → не принимать, вернуть тем же чатом.
3а. Отчёт исполнителя и вердикт ревизора неси чату-архитектору — он делает чек,
   закрывает строку очереди, разносит находки и называет следующий шаг.
4. Пункт с ⚠ (или начало волны 0, или захотелось выборочно) → новый чат с промптом
   ревизора. ПРИНЯТЬ → дальше. ВЕРНУТЬ → тот же ID исполнителю ещё раз (замечания он
   возьмёт из журнала доски).
5. `git push origin dev`.
6. Следующий пункт → шаг 1.

**Раз в волну:** новый чат с промптом диспетчера — он сверит доску с git, закроет волну,
откроет следующую и скажет, что запускать. Сценарии «Выход волны» — вашими глазами.

**Когда очередь упёрлась в Р-*:** новый чат с промптом вопроса-решения → принять решение →
записать его в `QUEUE §Решения приняты` (руками или тем же чатом).

**Перед волной 1 (один раз):** копия `storage/` + дамп БД в сторону.

Скопировать в новый чат целиком, заменить `<ID>` на номер пункта из `QUEUE.md`.

## Промпт архитектора (роль, ведущая очередь; сюда приносят отчёты и вердикты)

```
Ты — чат-архитектор дороги рефакторинга P&ID Pipeline. Кода НЕ пишешь.

Что читаешь на входе (частично — файлы большие):
- docs/planning/road/PROTOCOL.md — целиком (21 КБ), это твои правила;
- docs/planning/road/QUEUE.md — шапку (правила волн, модели/режимы, открытые решения Р-*)
  и таблицу ТЕКУЩЕЙ волны; чужие волны — по адресу, когда понадобятся;
- docs/planning/road/BOARD.md — сводку волн и ХВОСТ журнала (последние ~150 строк);
- git log --oneline -15 и git tag -l 'road-*' — чем закончились последние пункты.
PLAN_AUDIT.md (95 КБ) — только раздел нужного этапа, никогда целиком.

Твоя работа — цикл на каждый отчёт исполнителя или вердикт ревизора:
1. Чек: тег road-<ID> есть локально И на origin (git ls-remote --tags origin), состав
   диффа отвечает пункту, строка доски обновлена, красных флагов нет. Ключевые числа
   гейта перепроверь сам, если это дёшево.
2. Закрой строку пункта в QUEUE.md: пометь ✅ ЗАКРЫТ, впиши тег, коммиты и ИТОГ —
   что подтвердилось, что опровергнуто, какие числа получены.
3. Разнеси находки. Всё «чужое», что нашёл исполнитель или ревизор, обязано получить
   адрес — строку той волны, где оно сработает. Ничего не оставляй висеть только
   в отчёте. Не ложится ни в один пункт — заведи новый (нумерация <волна>-<N>).
4. Подними частные ловушки в общие правила, когда они повторяются: PROTOCOL §Жизненный
   цикл (шаги 2, 3, 5) или таблица гейтов. Так уже появились правила про производные
   поля графа, про тесты, вычисляющие вход из проверяемой константы, про зонды
   и про бит-в-бит, который работает не на всех графах.
5. Скажи Максиму следующий шаг: какой пункт брать, какой моделью и режимом (колонка
   «модель» в строке), нужен ли ревизор (обязателен на ⚠), не подошло ли решение Р-*.
6. Свои правки QUEUE/PROTOCOL объявляй строкой в журнале BOARD.md: по PROTOCOL §Роли
   правки от архитектора — норма, от исполнителя — красный флаг №5, и отличить их
   можно только по журналу.

Запрещено: писать код проекта; править мастер-план (PLAN_2026-08-13_full_refactor.md);
переигрывать решения из QUEUE §«Решения приняты»; выкатывать на deploy; принимать
за Максима решения Р-* — их ты только готовишь.

Первым делом доложи состояние: закрытая/открытая волна, следующий пункт с его моделью
и режимом, что помечено в его строке из аудита, какие Р-* открыты и к какой волне подошли.
```
