# Плейбук: как внедряем, тестируем и расширяем (послойно)

## Статус: что «готово», а что делается по волнам

- **Готов дизайн/блюпринт** (стабилен): канон фаза→под-шаг, таксономия ошибок (база + семейства + CVAT), маппинг стадия→контейнер, основные точки вставки, решения по прогрессу/ретеншну/статистике.
- **Делается по волнам** (в коде, с проверкой): поштучная карта вставок в каждом файле + листовые типы ошибок. Их нельзя надёжно перечислить наперёд — видно только в коде и проверяется прогоном. Поэтому не «один гигантский список», а **повторяемый цикл**.

---

## Цикл одной волны (одна стадия = одна волна)

1. **Locate.** Грепаем задачу стадии + её модули по каждому `except` / `raise` / `print` / горячему циклу → получаем line-level карту вставок этой стадии.
2. **Map.** Каждую точку → на границу `step()` и/или доменный тип ошибки. Недостающие листовые типы дописываем в `errors.py`.
3. **Implement.** Оборачиваем под-шаги в `step()`, `print→logger` (или через мост), меняем широкие/немые `except` на узкие+типизированные, в fail-путях пишем `error_code`/`failed_step`.
4. **Test** (ниже, без GPU).
5. **Verify completeness** — чек-лист по грепу (ниже).
6. **Review** — дифф → мердж. Каждая волна самостоятельна и обратима.

---

## Как тестируем (на CPU, без GPU, без риска для боевого)

Ключевая идея: тестируем **обвязку логов/ошибок**, а не тяжёлый инференс — значит модели и GPU не нужны.

- **A. Юнит-тесты примитивов** (один раз, в фундаменте): `step()` пишет start/end/duration; при исключении оборачивает+логирует+пробрасывает типизированное; `fail_stage` пишет `error_code`+`failed_step`; `contextvars`-фильтр вставляет `uid/stage/task_id` в запись; у ошибок есть `.code`/`.stage`.
- **B. Fault injection по стадии** (главный приём). Форсируем каждую ветку отказа **без реального прогона**:
  - нет входного артефакта → ждём `ArtifactMissingError` + `error_code` + строку лога + стадию `FAILED`;
  - мок CVAT-клиента отдаёт 500 / таймаут / пустой zip / битый json → ждём `CVATRequestError`/`CVATTimeoutError`/`CVATExportError` и записанные поля;
  - monkeypatch тяжёлого вызова, чтобы бросил (имитация OOM) → ждём `InferenceError` + трейсбек.
  Проверяет проводку ошибок/логов без весов и GPU.
- **C. Фикстуры для клиента.** Вставляем фейковые строки `processing_stages` (RUNNING со `started_at` → прогресс-бар; FAILED с `error_traceback`+`error_code` → окно ошибки) и проверяем, что клиент рисует процент и отчёт. Пайплайн гонять не нужно.
- **D. Smoke-прогон стадии на CPU.** Одна маленькая реальная диаграмма через стадию: в логах есть баннер, под-шаги с таймингом, `grep <uid>` даёт полную хронологию, а специально вызванный сбой проходит сквозняком worker → БД → `/stages` → окно клиента.
- **E. Golden-path.** Одна крошечная диаграмма end-to-end (насколько тянет CPU) — проверяет, что корреляция работает через `api`+`worker`+`worker_ocr`.

A–C гоняются в CI без сервера; D–E — на копии/стенде.

---

## Verify completeness (чтобы «все места» были закрыты по-настоящему)

По каждой стадии — чек по грепу до/после:
- `print(` в модуле стадии → **0** (или всё идёт через мост);
- нет `except:`/`except Exception` без `logger.*(exc_info=True)` — голых `pass` не осталось;
- каждый `raise` в пайплайн-коде — типизированный (`PipelineError`-потомок);
- у стадии есть баннер на старте и `duration` на конце каждого под-шага;
- `/stages` по тестовой диаграмме отдаёт `error_code`+`failed_step`+`traceback`.

Это можно вынести в мелкий CI-линт (запрет `except: pass`, запрет `print(` в `worker/`/`modules/`).

## Как расширяем со временем

- **Иерархия растёт листьями** — на каждой волне добавляем конкретные типы по мере того, как в коде видно, что recoverable, а что фатально. База+семейства уже есть.
- **Обратная связь от статистики**: недельные данные `processing_stages` показывают, какие стадии чаще падают и где дольше всего → туда идёт более глубокая инструментация в первую очередь.
- **Новая внешняя интеграция** → новое семейство ошибок по тому же принципу (как CVAT).

---

## Безопасность и выкатка (важно на CPU-сервере)

- **Изменения аддитивные и поведение-сохраняющие**: те же сбои падают так же, просто теперь записаны и видны. Вычисление и параллелизм не трогаем.
- **Ветка → стенд/копия → бой.** Не правим прямо на живом сервере; проверяем на локальном docker-compose или копии.
- **Волна за волной, каждая обратима.** Если что-то не так — откат одной волны, а не всего.
- **Мост `print→logging` закрывает переход**: даже не мигрированные `print` уже текут в тегированные логи — «дыры» во время миграции нет.

## Порядок волн

0. **Фундамент** + юнит-тесты (A): `errors.py`, `obs.py` (`step`/`bind`/artifact I/O), `contextvars`-фильтр и формат, миграция `error_code`+`failed_step`, `celery_task_id` в `/stages`, мост `print→logging`, ротация docker-логов.
1. **CVAT** (текущая боль) — полная карта вставок + fault-injection (B).
2. **Клиент**: прогресс + окно ошибки (на фикстурах C) — можно параллельно после фундамента.
3. **Остальные стадии** волнами: detection → segmentation/skeleton/graph → ocr/junction/contours/fxml → upload/frame.
4. **Недельная сводка** по `processing_stages`.

Каждая волна: Locate → Map → Implement → Test → Verify → Review. Одинаково для всех — это и есть гарантия, что «все места» закрываются системно, а не на глаз.
